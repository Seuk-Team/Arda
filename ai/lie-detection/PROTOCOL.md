# 실시간 면접 WebSocket 프로토콜

> 지원자 화면(웹·앱) ⟷ 거짓말 탐지 워커 · ADR-0029 · 2026-09-07
> 이 문서가 원본이다. 값을 바꾸면 `interview_ws.py` 와 같이 고친다.

```
wss://api.seuk.suvisdev.cloud/ai/ws/interview/{token}
```

`token` 은 메일 링크의 그 토큰이다. 별도 로그인은 없다.

---

## 붙기 전에 해야 할 것

WebSocket 은 **면접이 이미 시작된 뒤**에만 붙는다. 동의와 시작은 기존 REST 로 먼저 끝낸다.

```
POST /api/v1/public/interview/{token}/consent   { "agreed": true }
POST /api/v1/public/interview/{token}/start
→ 그 다음 WebSocket 접속
```

시작하지 않은 채 붙으면 서버가 `error` 를 보내고 연결을 닫는다.

---

## 보내는 것 (지원자 → 서버)

### 바이너리 — 첫 바이트가 종류다

| 첫 바이트 | 무엇 | 형식 |
|---|---|---|
| `0x01` | 오디오 | **16kHz · 16-bit · mono PCM** (little-endian) |
| `0x02` | 영상 프레임 | JPEG |

```js
const packet = new Uint8Array(1 + payload.byteLength)
packet[0] = 0x01                    // 오디오
packet.set(new Uint8Array(payload), 1)
ws.send(packet)
```

**오디오는 `MediaRecorder` 가 아니라 Web Audio API 로 보낸다.** `MediaRecorder` 는
webm/opus 를 내는데, 그걸로 발화 끝을 알아내려면 서버가 매번 디코딩해야 하고
실시간 예산(1.5초)을 먹는다. PCM 이면 산술만으로 끝난다.

```js
const ctx = new AudioContext({ sampleRate: 16000 })
await ctx.audioWorklet.addModule('pcm-worklet.js')   // Float32 → Int16 변환만 하는 워크릿
```

권장 주기 — 오디오 **50ms 마다**, 영상 **초당 5~10장**. 영상은 더 자주 보내도
서버가 3장에 1장만 본다.

**조각 크기는 맞추지 않아도 된다.** 서버가 바이트 수로 시간을 세므로 20ms 든
200ms 든 판정이 같다(2026-09-09). 전에는 조각 **개수**로 셌고, 그래서 앱이
1600바이트로 다시 잘라 보내야 했다 — 이제 그럴 필요가 없다. 다만 너무 크게
묶으면(0.5초 이상) 말이 끝난 것을 알아채는 시점이 그만큼 늦어진다.

### 텍스트 — JSON

| | |
|---|---|
| `{"type":"ping"}` | 연결 유지. 서버가 `pong` 으로 답한다 |

## 받는 것 (서버 → 지원자)

전부 JSON 이다.

| `type` | 언제 | 같이 오는 것 |
|---|---|---|
| `question` | 접속 직후, 그리고 답변이 저장될 때마다 | `seq`, `text` |
| `listening` | 말을 시작한 것을 감지했을 때 | |
| `processing` | **마지막 답변**의 전사를 기다리는 중 | 중간 질문에서는 안 온다 |
| `retry` | 말이 안 담겨 답변으로 세지 않았을 때 | `message`. **질문 목록을 못 받은 경우에만** |
| `done` | 남은 질문이 없을 때. **서버가 세션도 닫는다**(`finish` 를 따로 부르지 않아도 된다) | |
| `error` | 문제가 생겼을 때 | `message`, (있으면) `status` |

```json
{ "type": "question", "seq": 2, "text": "820ms 중 어디가 오래 걸리는지 어떻게 좁혀 가셨어요?" }
```

**`listening` 과 `processing` 을 화면에 꼭 표시해 주세요.** 1~2초 공백에
지원자가 "멈췄나?" 하고 생각하면 그 자체가 면접을 망칩니다.

## 말이 끝난 것을 서버가 판정한다

지원자가 "제출" 버튼을 누르지 않는다. 서버가 소리를 듣고 판정한다.

**답을 마친 뒤 3초는 기다리게 된다.** 짧게 잡으면 생각하느라 쉬는 도중에 끊고
들어가 답변이 반토막으로 저장되는데, 그건 되돌릴 수 없다. 기다리는 쪽이 낫다고 보고
길게 잡았다 — 화면에서 그 3초 동안 "듣고 있습니다" 를 계속 보여 주면 된다.
값은 서버 `SILENCE_END_SEC` 로 바꿀 수 있다(재배포 불필요, 컨테이너 재시작만).

| 값 | 지금 | 뜻 |
|---|---|---|
| 침묵 판정 | **3초** | 이만큼 조용하면 말이 끝난 것으로 본다 |
| 최소 발화 | **0.7초** | 이보다 짧으면 답변으로 세지 않는다 (기침·문 닫는 소리) |
| 최대 발화 | **180초** | 여기서 강제로 끊는다 |

소리 기준은 고정값이 아니라 **배경 소음**에서 잡고, 그 뒤로도 계속 따라간다.

**폰은 `getUserMedia` 직후 첫 버퍼들을 0 으로 준다.** 그 무음은 보정에 넣지 않으므로
마이크가 실제로 소리를 내보내기 시작해야 기준이 잡힌다(약 0.5초). 그래서 붙자마자
말하면 판정이 늦다 — 화면에서 **"준비 중"을 잠깐 보여 주고** 시작하는 편이 낫다.

2026-09-08 운영 실측에서 이 무음이 보정에 섞여 임계값이 낮게 앉았고, 생활 소음에
계속 "말하는 중"이 되어 **질문이 넘어가지 않았다.** 지금은 바닥값이 스스로 따라가
몇 초 안에 회복한다.

---

## 판정은 이 소켓으로 오지 않는다

말하는 동안 서버가 1초마다 진위 판정을 굴리지만, **지원자 화면으로는 보내지 않는다.**
화면에 안 그려도 개발자 도구를 열면 보이고, 거기서 ADR-0029 의 "지원자에게 판정을
보여 주지 않는다"가 깨진다.

```
워커 → POST /api/v1/internal/interview/{token}/verdict → 백엔드 → 담당자 화면
```

`ARDA_SERVICE_TOKEN` 이 워커에 없으면 보내지 않는다(설정을 넣어야 켜진다).

## 끊겼을 때

**끊긴 것 자체는 오류가 아니다.** 답변은 백엔드에 저장돼 있고, 다시 붙으면
**아직 답하지 않은 가장 앞 질문**부터 이어진다. 재접속만 하면 된다.

다만 재접속하면 배경 소음 보정을 처음부터 다시 한다.

## `/ws/live` 는 이제 데모 전용이 아니다 (2026-09-09 · woojeongalex)

**사람 대 사람 화상 면접에서 채용자 화면이 이 소켓을 씁니다.** 지우거나 규격을
바꾸실 때 알려 주세요.

```
채용자 브라우저 (/interview-room/{id})
  └─ 지원자에게서 WebRTC 로 받은 영상·소리를 그대로
       → wss://…/ai/ws/live   (0x01 PCM · 0x02 JPEG, /ws/interview 와 같은 형식)
       ← {"type":"live", ok, truth_pct, lie_pct, signals} · speaking · quiet
```

**왜 지원자 기기가 아니라 채용자 기기가 보내는가**: 화상 면접은 영상이 두
브라우저 사이를 직접 오가서 워커가 볼 길이 없습니다. 지원자 쪽에서 보내면 판정을
받는 자리가 지원자 기기가 되어 ADR-0029 가 다시 깨지는데(#97 에서 겪은 것),
채용자가 **자기가 이미 받아 보고 있는 영상**을 넘기면 그 문제가 아예 없습니다.
지원자 쪽은 아무것도 더 하지 않습니다.

`/ws/interview/{token}` 쪽(AI 면접)은 그대로입니다 — 그쪽 판정은 워커가
백엔드(`POST /internal/interview/{token}/verdict`)로 밀어 주시면 됩니다.

프론트는 `frontend/app/src/pages/useLiveAnalysis.ts` 입니다.

## 아직 비어 있는 것

**전사는 붙었지만 기본이 꺼짐이다**(ADR-0032). 서버에 `STT_MODEL` 이 없으면
`[전사 꺼짐 · 발화 3.2초]` 가, 모델을 못 올리면 `[전사 불가 · …]` 가 저장된다.
어느 쪽이든 **흐름(질문 → 답변 → 다음 질문)은 그대로 돈다.**

말이 안 담긴 답변은 저장하지 않고 `retry` 를 보낸다 — whisper 가 무음에
"감사합니다." 를 지어내기 때문이다(실측). 화면은 이 메시지를 받으면 같은 질문을
그대로 두고 다시 답하게 하면 된다.

---

## 정해야 하는 것

- **카메라·마이크를 못 켜는 지원자를 어떻게 할 것인가.** 실시간이 전제라 지금 설계에는
  텍스트로 답하는 길이 없다. 그대로 두면 기기·권한 문제가 지원 자격이 된다
- 답변당 제한 시간을 화면에 보여 줄 것인가 (서버 상한은 180초)
- 연결이 자주 끊길 때 안내 문구

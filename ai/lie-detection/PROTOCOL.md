# 실시간 면접 WebSocket 프로토콜

> 지원자 화면(웹·앱) ⟷ 거짓말 탐지 워커 · ADR-0029 · 2026-09-07
> 이 문서가 원본이다. 값을 바꾸면 `interview_ws.py` 와 같이 고친다.

```
wss://api.seuk.suvisdev.cloud/ai/ws/interview/{token}              ← 지원자 기기
wss://api.seuk.suvisdev.cloud/ai/ws/interview/{token}?role=recruiter  ← 담당자 방 (얼굴만)
```

`token` 은 메일 링크의 그 토큰이다. 별도 로그인은 없다.

## 한 면접에 소켓 둘 (2026-09-16)

**`role` 은 기본이 `applicant` 다** — 지금까지 붙던 쪽은 아무것도 안 바꿔도 된다.

| `role` | 보내는 것 | 받는 것 |
|---|---|---|
| `applicant` (기본) | 소리(`0x01`) · 얼굴(`0x02`) · `end`·`ping` | 질문 · `listening` · `processing` · `retry` · `done` |
| `recruiter` | **얼굴(`0x02`)만** · `ping` | `{"type":"ready","role":"recruiter"}` · `pong` |

**왜 나눴나**: 앱은 2026-09-09 개편에서 영상을 WebRTC 로 보내게 바뀌어 얼굴 JPEG 을 한 장도 안 보낸다. 서버는 WebRTC 미디어 경로에 없어(백엔드는 신호만 중계한다) 그 영상을 볼 수 없다. 그런데 **담당자 방은 그 영상을 이미 받아 그리고 있다** — 거기서 프레임을 떠 보내면 얼굴 신호가 살아난다.

소리는 그럴 수 없다. 앱이 WebRTC 를 `audio: false` 로 열어(안드로이드가 `AudioRecord` 를 하나만 준다) **담당자가 받는 스트림에는 소리 트랙이 없다.** 그래서 소리는 원본을 가진 앱이, 얼굴은 이미 받은 담당자가 보낸다.

**두 소켓은 같은 세션 장부를 쓴다** — 소리와 얼굴이 합쳐져야 판정이 난다. 따로 두면 한쪽은 `no_face`, 다른 쪽은 `short_audio` 로 아무 판정도 안 난다.

**담당자 소켓은 답변 흐름에 끼지 않는다.** 질문을 두 벌 보내면 담당자 화면이 지원자 행세를 하고, `end`(답변 완료)가 두 곳에서 오면 같은 답변이 두 번 끝난다. 담당자가 보낸 소리(`0x01`)는 **버린다** — 무음이 지원자 목소리에 섞이면 전사가 망가진다.

담당자 방이 빠져도 면접은 이어진다(그 반대도 같다). 마지막 소켓이 빠질 때 세션을 버린다.

**얼굴 출처는 한 면접에 하나다 — 지원자 우선** (2026-09-17, 민아님 제안 (가)). 웹 지원자 페이지는 자기 카메라를 직접 보내고, 담당자 방은 WebRTC 로 받은 같은 얼굴을 한 번 더 떠서 보낸다. 둘 다 받으면 `recv` 가 두 배가 되고 같은 순간이 판정 창에 두 번 들어간다. 그래서:

| 상황 | 쓰는 얼굴 |
|---|---|
| 지원자 소켓에서 **최근 3초 안에** 얼굴이 왔다 (웹 지원자) | 지원자 것만. 담당자 것은 버리고 `dropped_recruiter` 로 센다(`recv` 에 안 든다) |
| 지원자가 얼굴을 안 보낸다 (앱 지원자) · 지원자 전송이 3초 넘게 멈췄다 | 담당자 것 |

3초는 `APPLICANT_VIDEO_FRESH_SEC`. `/health` 의 `frames.dropped_recruiter` 와 끝날 때 로그의 `담당자중복버림=` 으로 볼 수 있다. **앱 면접은 지금과 똑같다.**

## 붙기 전에 해야 할 것

WebSocket 은 **면접이 이미 시작된 뒤**에만 붙는다. 동의와 시작은 기존 REST 로 먼저 끝낸다.

```
POST /api/v1/public/interview/{token}/consent   { "agreed": true }
POST /api/v1/public/interview/{token}/start
→ 그 다음 WebSocket 접속
```

시작하지 않은 채 붙으면 서버가 `error` 를 보내고 연결을 닫는다.

## 보내는 것 (지원자 → 서버)

### 바이너리 — 첫 바이트가 종류다

| 첫 바이트 | 무엇 | 형식 |
|---|---|---|
| `0x01` | 오디오 | **16kHz · 16-bit · mono PCM** (little-endian) |
| `0x02` | 영상 프레임 | JPEG |

```js
const packet = new Uint8Array(1 + payload.byteLength)
packet[0] = 0x01                    // 오디오
packet.set(new Uint8Array(payload), 1)
ws.send(packet)
```

**오디오는 `MediaRecorder` 가 아니라 Web Audio API 로 보낸다.** `MediaRecorder` 는
webm/opus 를 내는데, 그걸로 발화 끝을 알아내려면 서버가 매번 디코딩해야 하고
실시간 예산(1.5초)을 먹는다. PCM 이면 산술만으로 끝난다.

```js
const ctx = new AudioContext({ sampleRate: 16000 })
await ctx.audioWorklet.addModule('pcm-worklet.js')   // Float32 → Int16 변환만 하는 워크릿
```

권장 주기 — 오디오 **50ms 마다**, 영상 **초당 5~10장**. 영상은 더 자주 보내도
서버가 3장에 1장만 본다.

**조각 크기는 맞추지 않아도 된다.** 서버가 바이트 수로 시간을 세므로 20ms 든
200ms 든 판정이 같다(2026-09-09). 전에는 조각 **개수**로 셌고, 그래서 앱이
1600바이트로 다시 잘라 보내야 했다 — 이제 그럴 필요가 없다. 다만 너무 크게
묶으면(0.5초 이상) 말이 끝난 것을 알아채는 시점이 그만큼 늦어진다.

### 텍스트 — JSON

| | |
|---|---|
| `{"type":"ping"}` | 연결 유지. 서버가 `pong` 으로 답한다 |
| `{"type":"end"}` | **[답변 완료]** (2026-09-09). 지금까지 보낸 소리를 답변으로 끊는다. 서버가 `processing` 을 보내고 **받아쓴 뒤** 글이 있으면 저장하고 다음 `question`(또는 `done`), 비었으면 `retry`. 버퍼가 0.7초도 안 되면 바로 `retry`. **2026-09-15 부터 답변을 끝내는 유일한 길이다**(아래) |

## 받는 것 (서버 → 지원자)

전부 JSON 이다.

| `type` | 언제 | 같이 오는 것 |
|---|---|---|
| `question` | 접속 직후, 그리고 답변이 저장될 때마다 | `seq`, `text` |
| `listening` | 말을 시작한 것을 감지했을 때 | |
| `processing` | [답변 완료] 뒤 받아쓰는 중 (짧은 답 1~3초 · 3분 답 ~20초) | 화면에 "정리하는 중" |
| `retry` | 받아쓴 글이 비어 답변으로 세지 않았을 때. **같은 질문이 그대로 남는다** | `message` |
| `done` | 남은 질문이 없을 때. **서버가 세션도 닫는다**(`finish` 를 따로 부르지 않아도 된다) | |
| `error` | 문제가 생겼을 때 | `message`, (있으면) `status` |

```json
{ "type": "question", "seq": 2, "text": "820ms 중 어디가 오래 걸리는지 어떻게 좁혀 가셨어요?" }
```

**`listening` 과 `processing` 을 화면에 꼭 표시해 주세요.** 1~2초 공백에
지원자가 "멈췄나?" 하고 생각하면 그 자체가 면접을 망칩니다.

## 답변 끝은 [답변 완료] 버튼이 정하고, 답변인지는 전사가 정한다 (2026-09-15 개정)

**조용해진 것만으로는 다음 질문으로 넘어가지 않는다**(2026-09-11). 3초 침묵으로 넘기던
때는 문장 사이에 쉰 순간 끊겨 답이 반토막 나고(세션 59), 폰 스피커 소리가 질문을
넘겼다(세션 57).

09-11 판은 "이상입니다" 로도 끝냈고, 넘기기 전에 VAD 로 사람 목소리를 쟀다. 둘 다
2026-09-15 에 뺐다:
- "이상입니다" 확인용 전사가 **무음에 "이상입니다" 를 지어내**(whisper hallucination)
  지원자가 짧게 답하고 조용해진 것뿐인데 답변이 강제로 끊겼다(세션 77).
- VAD 가 앱이 보내는 소리를 자주 "목소리 0초" 로 봐서 실제 답변이 계속 튕겼다
  (세션 YL4qeYLK: 9번 눌러 8번 `retry`).

이제 흐름은 하나다:

1. 지원자가 **[답변 완료]** — `{"type":"end"}` (앱·웹 모두 버튼이 있다)
2. 서버가 `processing` 을 보내고 **여기까지의 소리를 받아쓴다** (API · 짧은 답 1~3초.
   `STT_BACKEND` 가 비어 로컬 CPU 전사면 2 vCPU 에서 30~100초)
3. 글이 있으면 → 저장(`answered` 표시 + 전사) → 다음 `question` 또는 `done`
   글이 없으면 → `retry` · **같은 질문 그대로** · 소리는 버리지 않고 다음 답에 앞에 붙인다

**받아쓰는 동안에도 서버는 소켓을 계속 읽는다** (2026-10-13). `ping` 에 `pong` 이
가고, 그 사이 보낸 소리는 버퍼에 쌓여 **다음 답변의 앞부분**이 된다(`listening` 은
안 보낸다). 그 전에는 전사를 기다리는 동안 읽기가 멈춰 uvicorn 의 keepalive 가
pong 을 못 받고 **20~40초 뒤 `1011 keepalive ping timeout` 으로 소켓을 끊었다** —
로컬 전사가 그보다 오래 걸리면 답변마다 끊겼다(10-13 실측). 클라이언트는 그래도
닫힘(`onclose`)을 보고 알려야 한다 — 아래 「끊겼을 때」.

받아쓴 글 끝의 "이상입니다" 류는 뗀다(답변 내용이 아니라 습관적 마무리). 무음·잡음에
whisper 가 지어낸 조각은 전사 층에서 거른다(`no_speech_prob` · `STT_NO_SPEECH_MAX`).

| 값 | 지금 | 뜻 |
|---|---|---|
| 답변 상한 | **180초** (`MAX_ANSWER_SEC`) | 버튼 없이 이만큼 이어지면 끊는다. 첫 말부터 센다 |
| 최소 발화 | **0.7초** | 이보다 짧으면 버튼을 눌러도 `retry` (기침·문 닫는 소리) |
| 멈춤 | **1.2초** (`PAUSE_CHECK_SEC`) | `listening` 배지가 꺼지는 기준일 뿐, 답변을 끝내지 않는다 |

서버 `/health` 의 `answers` 에 저장한 답(`saved`)·전사가 빈 답(`empty`)과 어떻게
끝났는지(`by_button` · `by_limit`)가 쌓인다.

소리 기준은 고정값이 아니라 **배경 소음**에서 잡고, 그 뒤로도 계속 따라간다.

**폰은 `getUserMedia` 직후 첫 버퍼들을 0 으로 준다.** 그 무음은 보정에 넣지 않으므로
마이크가 실제로 소리를 내보내기 시작해야 기준이 잡힌다(약 0.5초). 그래서 붙자마자
말하면 판정이 늦다 — 화면에서 **"준비 중"을 잠깐 보여 주고** 시작하는 편이 낫다.

2026-09-08 운영 실측에서 이 무음이 보정에 섞여 임계값이 낮게 앉았고, 생활 소음에
계속 "말하는 중"이 되어 **질문이 넘어가지 않았다.** 지금은 바닥값이 스스로 따라가
몇 초 안에 회복한다.

## 판정은 이 소켓으로 오지 않는다

말하는 동안 서버가 1초마다 진위 판정을 굴리지만, **지원자 화면으로는 보내지 않는다.**
화면에 안 그려도 개발자 도구를 열면 보이고, 거기서 ADR-0029 의 "지원자에게 판정을
보여 주지 않는다"가 깨진다.

```
워커 → POST /api/v1/internal/interview/{token}/verdict → 백엔드 → 담당자 화면
```

`ARDA_SERVICE_TOKEN` 이 워커에 없으면 보내지 않는다(설정을 넣어야 켜진다).

## 끊겼을 때

**끊긴 것 자체는 오류가 아니다.** 답변은 백엔드에 저장돼 있고, 다시 붙으면
**아직 답하지 않은 가장 앞 질문**부터 이어진다. 재접속만 하면 된다.

다만 재접속하면 배경 소음 보정을 처음부터 다시 한다.

## `/ws/live` 는 이제 데모 전용이 아니다 (2026-09-09 · woojeongalex)

**사람 대 사람 화상 면접에서 채용자 화면이 이 소켓을 씁니다.** 지우거나 규격을
바꾸실 때 알려 주세요.

```
채용자 브라우저 (/interview-room/{id})
  └─ 지원자에게서 WebRTC 로 받은 영상·소리를 그대로
       → wss://…/ai/ws/live   (0x01 PCM · 0x02 JPEG, /ws/interview 와 같은 형식)
       ← {"type":"live", ok, truth_pct, lie_pct, signals} · speaking · quiet
```

**왜 지원자 기기가 아니라 채용자 기기가 보내는가**: 화상 면접은 영상이 두
브라우저 사이를 직접 오가서 워커가 볼 길이 없습니다. 지원자 쪽에서 보내면 판정을
받는 자리가 지원자 기기가 되어 ADR-0029 가 다시 깨지는데(#97 에서 겪은 것),
채용자가 **자기가 이미 받아 보고 있는 영상**을 넘기면 그 문제가 아예 없습니다.
지원자 쪽은 아무것도 더 하지 않습니다.

`/ws/interview/{token}` 쪽(AI 면접)은 그대로입니다 — 그쪽 판정은 워커가
백엔드(`POST /internal/interview/{token}/verdict`)로 밀어 주시면 됩니다.

프론트는 `frontend/app/src/pages/useLiveAnalysis.ts` 입니다.

## 아직 비어 있는 것

**전사는 설정을 넣어야 켜진다.** `STT_BACKEND=openai` + `OPENAI_API_KEY` 면 OpenAI
전사 API 를 쓴다(2026-09-15, ADR-0038 — 2 vCPU 로컬 전사는 44초 발화가 180초 상한을
넘겨 `[전사 지연 · …]` 이 저장됐다). 로컬 전사는 `STT_MODEL`(ADR-0032) — GPU 가 있거나
오디오를 밖으로 못 보낼 때.

**`STT_BACKEND` 가 비어 있으면 이 서버는 로컬로 받아쓴다 — 백엔드는 같은 빈 값을
`openai` 로 읽는다.** 두 컨테이너가 같은 `backend/.env` 를 읽는데 해석이 갈린다
(ADR-0038 「같은 변수, 두 해석」). **2026-09-17 실측 운영 값은 빈 값**이다 — 그래서
지금 운영의 실시간 전사는 API 가 아니라 **CPU 로컬(`STT_MODEL`)** 이다. 이 문서가
전에 "프로덕션은 openai" 라고 적어 두어 조사하던 사람이 경로를 잘못 짚었다. 운영이
어느 쪽인지는 `/ai/health` 가 아니라 서버 `.env` 로 확인한다. 둘 다 없으면 `[전사 꺼짐 · 발화 3.2초]`
가, 모델을 못 올리거나 API 가 죽었는데 로컬도 없으면 `[전사 불가 · …]` 가 저장된다.
어느 쪽이든 **흐름(질문 → 답변 → 다음 질문)은 그대로 돈다.**

**전사할 때 면접 질문을 힌트로 준다** (2026-09-10). whisper 의 `initial_prompt`
자리에 그 면접의 질문들을 넣으면 거기 나온 낱말을 후보로 먼저 놓는다 — 실측:
"데이터베이스 퀄리" → "데이터베이스 쿼리", "엘라스틱 서치" → "엘라스틱서치".
속도는 그대로다(12.8초 → 12.8초).

용어 목록을 코드에 박지 않는다 — 그러면 IT 면접에만 맞는다. **말하지 않은 낱말이
전사에 새지 않는 것도 확인했다**: 질문에만 있는 말 4개(테라폼·코틀린·러스트·선호)와
없는 낱말 60개를 넣어도 전사가 그대로였다. 전사는 대조에서 원문 그대로 인용되므로
이 확인이 없으면 쓸 수 없다.

말이 안 담긴 답변은 저장하지 않고 `retry` 를 보낸다 — whisper 가 무음에
"감사합니다." 를 지어내기 때문이다(실측). 화면은 이 메시지를 받으면 같은 질문을
그대로 두고 다시 답하게 하면 된다.

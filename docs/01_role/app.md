## 1. 미션

담당자·면접관용 **모바일 네이티브 앱**. 이동 중에 지원자를 확인하고 단계를 바꾸고 평가를 남긴다. 웹과 **같은 API**를 쓰는 두 번째 클라이언트 — "API를 제대로 설계하면 클라이언트가 몇 개든 붙는다"를 증명하는 트랙이다.

## 2. 스택 (확정 — [ADR-0010](../03_decision/0010-앱-flutter-확정.md))

**Flutter (Dart).** 실개발·시연은 **Android 전용**, iOS는 코드 호환만 유지한다.

- 자체 렌더링 엔진이라 화면이 OS와 무관하게 동일하고, 위젯 카탈로그가 넓어 서드파티 의존이 적다
- 디자인 토큰·화면 지도(05-design)는 CSS 값 → Dart `ThemeData`로 **수동 이식**한다 (웹의 `frontend/app/src/tokens.css`가 원본)
- **실기기 배포는 Android만** — 팀 Android 4대 + 에뮬레이터가 개발·시연 대상이다
- **iOS는 코드 호환까지만** — iOS 지원 플러그인만 쓰고 플랫폼 분기를 안 남긴다. **Mac이 없어 iOS 빌드 검증은 불가능하며, 이를 "iOS 지원"이라 주장하지 않는다**
- 데모 범위를 Android로 좁힌 전제 위의 확정이다 — 근거와 감수 사항은 [ADR-0010](../03_decision/0010-앱-flutter-확정.md)

## 3. 범위

**포함** — 로그인(JWT) · 공고 리스트 · 지원자 리스트(단계 탭 필터 + 퍼널 바) · 지원자 상세(지원 정보 · **단계 이력**·**평가 목록**은 별도 화면) · **단계 변경**(드래그 대신 확인 시트 — 기획 §2-3) · 평가 작성 · 이력서 열람(presigned URL).

**2026-09-01 확대** — 웹이 사이드바 6개로 커지면서 앱도 그 지도를 따라간다. 위 목록에 더해:

| 화면 | 근거 | 웹과 다르게 간 곳 |
|---|---|---|
| **하단 탭바** (`공고 · 지원자 · 홈 · 캘린더 · 더보기`) | 05-design §9 는 768px 아래에서 "사이드바 접기"까지만 정하고 **대체 수단을 비워 뒀다** — 이 배치는 앱 오너 판단이다 | 탭은 5칸이 한계라 사이드바 6개 중 **평가 현황·설정을 더보기 안으로** 넣었다. 홈은 가운데(엄지 자리) |
| **대시보드**(홈) | 05-design §0.5 "요약 + 진입점" | §0.5 의 배치(숫자 카드 3장 → 지원자 현황 블록 → 캘린더 축소판 + 공고 퍼널 2열)는 넓은 화면 기준이다. 폰은 위에서부터 읽으므로 **급한 순**으로 다시 세웠다: 오늘 면접 → 내 리뷰 대기 → 전형 현황 → 진행중 공고. 지원자 현황 블록의 이름 나열은 **퍼널 한 줄 + 범례**로 접었고(폰에서 이름 10줄은 지원자 탭과 구별이 안 된다), 캘린더 축소판은 뺐다(축소판의 목적인 모프 전환이 앱엔 없다 — 캘린더가 탭이라 한 번이면 간다) |
| **캘린더** | 05-design 캘린더 절이 앱 동작을 직접 명시 | 문서 그대로 — **월 그리드 없음**, 주간 스트립(한 주 7칸·건수만) + 그날 목록. 이동도 달이 아니라 **주 단위**다 |
| **지원자**(전 공고 통합 검색) | 05-design §0.5 "전 공고 통합 검색 테이블 · 칸반 없음" | §9 "테이블은 카드형" 대로 6열을 카드로 폈다. **응답 시간 표기는 아직 없다** — 목데이터를 로컬에서 거르는 시간은 API 왕복이 아니라 성능 이야기가 못 된다. 큐 8에서 서버 값으로 붙인다 |
| **더보기** | 탭에 못 들어간 메뉴 + 사이드바 하단 프로필 자리 | 05-design 설정 절 그대로 — 프로필은 **표시 전용**(클릭 진입 없음), 사진 없이 **이니셜 아바타**(`users` 에 사진 컬럼이 없다) |
| **평가 현황**(평가 대기 큐) | 05-design §0.5 "내게 배정된 평가 대기 큐 + 우측 평가 패널" | 375px 엔 "우측"이 없어 큐만 두고, 누르면 그 사람의 평가 화면으로 넘어간다(§9). **§6 세 상태를 처음 다 갖춘 화면**이다 |

| **아르**(에이전트) | 05-design §0.5 전 화면 공통 진입점 · ADR-0009 "768px 이하는 덮는 오버레이" | 오버레이라 전체 화면 시트다. 진입점은 탭 화면에서 오른쪽 아래 버튼, 파고든 화면(상세)에서는 하단이 [단계 변경] 자리라 **상단 바 아바타**로 옮겼다. §1 AI 규약(앰버 점선 = 제안 / 잎초록 실선 = 사람 확정)을 그대로 지킨다 — 제안 카드의 승인 버튼은 `POST /agent/confirm` 자리이고 **지금은 잠겨 있다** |
| **설정** | 배포판 웹 설정 4탭 | 탭이 가로 스크롤이고 **전부 잠겨 있다**(내 정보 수정 API가 아직 없다). 문구는 웹 그대로 — 잠긴 이유를 화면에 적어 둔다 |
| **지원자 상세** | 앱 UI 초안 2026-09-01 (배포판 웹 상세 패널 기준) | 전형 레일 → **아르의 요약** → 지원 정보 → 메일 → 시스템 → 메모 → 단계 이력 순. 아르의 요약은 `ai_summary` 의 **JSON 을 웹과 같은 규격으로 파서** 요지 / 강점 / 확인 필요로 그린다(면접 확인 포인트는 값이 와도 안 그린다 — 05-design §0.5). 시안이 항목마다 카드 한 장으로 바꿨던 지원 정보는 필드가 7개로 늘면서 **한 카드 안 목록**으로 되돌렸다 |

**아직 안 만든 것** — **아르 서버 연동**(`POST /agent/chat` — 대화는 목데이터이고 입력칸은 잠금. 살아 있는 것처럼 보이면 데모에서 오해를 부른다) · 메일 발송·메모 쓰기·단계 변경의 **실제 저장**(전부 큐 8).

화면 설계 기준: [planning/00_summary_ko.md](../04_planning/00_summary_ko.md) 8장 + `frontend/mockups/mockup-mobile.html` + **모바일 시안(2026-08-28, 프론트 오너 작성)** + **앱 UI 초안(2026-09-01, 앱 오너 작성 — 배포된 웹 + 05-design 기준)**. 목업에 없던 5건(단계 변경 UI · 단계 이력 · 평가 목록 · 퍼널 바 배치 · 공고 리스트)을 시안이 채웠고, 그 과정에서 기존 화면의 치수도 함께 정해졌다 — **뒤에 온 것을 따른다: 목업 < 시안 < 앱 UI 초안.** 다만 **셋 중 무엇이든 05-design 과 어긋나면 05-design 이 이긴다** (초안이 `8월 28일 (금)` 로 그렸던 날짜를 §2 표기 통일에 맞춰 `2026.09.01` 로, 월 그리드 캘린더를 주간 스트립으로 바꾼 것이 그 사례다).

**제외** — 지원 폼(지원자용 외부 링크는 웹 전용) · 칸반(모바일 금지 원칙) · 앱 내 푸시 알림 G7(△ 여유 — 하게 되면 별도 합의) · 스토어 배포(데모는 Android APK 직접 전달, 여유 시 Play 내부 테스트 트랙까지) · **iOS 실기기 시연**(Mac 부재로 빌드 불가 — ADR-0010).

## 4. 인터페이스 계약

**의존** — 백엔드 API 전부 ([02-api.md](../00_overview/02-api.md)). **앱 때문에 API를 바꾸지 않는 것이 원칙** — 부족한 게 발견되면 백엔드 오너와 인터페이스 PR로 합의(그 자체가 발표 소재다). 인증 A1이 M2의 선행. **제공** — 없음 (순수 소비자. 그래서 격리가 가장 높다 — 앱이 실패해도 다른 파트가 안 죽는다).

## 7. 리스크

- **iOS 빌드 검증 불가** (Mac 없음) → 호환은 코드 규율로만 관리한다: iOS 지원 플러그인만 사용, `Platform.isAndroid` 분기 금지, `flutter analyze` 무경고. **"iOS도 된다"고 말하지 않는다** (ADR-0010).
- **Dart·Flutter 첫 사용 + 팀 내 사용자 0명** → 막히면 전부 혼자 푼다. SDK·`flutter doctor`·실기기 구동은 08/26 에 통과했으므로(#114) 남은 위험은 언어·프레임워크 자체다. 하루 안에 안 풀리면 팀 채널에 올린다.
- **개인 기기·개발 환경 편차** → M1에서 팀 Android 기기 전원에 APK 설치를 먼저 확인하고, 안 되는 기기는 데모 대상에서 뺀다. QR 즉시 반영이 없으므로 **배포 확인을 주 1회로 정기화**한다.
- **웹과 룩이 어긋남** → 토큰을 코드로 이식하고(임의 색 금지), 완료 기준에 목업·시안 대조 포함. **시안에 없는 값이 필요하면 만들지 말고 묻는다**(05-design §12) — 목업에 없던 5건이 그렇게 해결됐다.
- **백엔드 지연** → M1이 전부 API 무관. 전환기 큐로 본인이 선행을 만든다.

## 8. 면접 스토리

- **같은 API로 웹·앱 두 클라이언트** — 클라이언트 추가가 서버 변경 0으로 끝났는가, 아니면 무엇이 부족해 무엇을 바꿨는가
- 모바일에서 칸반을 버리고 리스트+단계 변경 버튼으로 간 **UX 재설계 근거** (기획 §2-3을 본인 언어로)
- **스택을 Flutter로 확정한 근거** ([ADR-0010](../03_decision/0010-앱-flutter-확정.md)) — 데모 범위를 Android로 좁히면서 무엇을 얻고 무엇을 포기했는지(iOS 실기기·웹 코드 재사용·QR 즉시 배포)까지 말할 수 있어야 한다

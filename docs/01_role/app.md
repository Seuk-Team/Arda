## 1. 미션

담당자·면접관용 **모바일 네이티브 앱**. 이동 중에 지원자를 확인하고 단계를 바꾸고 평가를 남긴다. 웹과 **같은 API**를 쓰는 두 번째 클라이언트 — "API를 제대로 설계하면 클라이언트가 몇 개든 붙는다"를 증명하는 트랙이다.

## 2. 스택 (확정 — [ADR-0010](../03_decision/0010-앱-flutter-확정.md))

**Flutter (Dart).** 실개발·시연은 **Android 전용**, iOS는 코드 호환만 유지한다.

- 자체 렌더링 엔진이라 화면이 OS와 무관하게 동일하고, 위젯 카탈로그가 넓어 서드파티 의존이 적다
- 디자인 토큰·화면 지도(05-design)는 CSS 값 → Dart `ThemeData`로 **수동 이식**한다 (웹의 `frontend/app/src/tokens.css`가 원본)
- **실기기 배포는 Android만** — 팀 Android 4대 + 에뮬레이터가 개발·시연 대상이다
- **iOS는 코드 호환까지만** — iOS 지원 플러그인만 쓰고 플랫폼 분기를 안 남긴다. **Mac이 없어 iOS 빌드 검증은 불가능하며, 이를 "iOS 지원"이라 주장하지 않는다**
- 데모 범위를 Android로 좁힌 전제 위의 확정이다 — 근거와 감수 사항은 [ADR-0010](../03_decision/0010-앱-flutter-확정.md)

## 3. 범위

**포함** — 로그인(JWT) · 공고 리스트 · 지원자 리스트(단계 탭 필터 + 퍼널 바) · 지원자 상세(지원 정보 · **단계 이력**·**평가 목록**은 별도 화면) · **단계 변경**(드래그 대신 확인 시트 — 기획 §2-3) · 평가 작성 · 이력서 열람(presigned URL).

**2026-09-01 확대** — 웹이 사이드바 6개로 커지면서 앱도 그 지도를 따라간다. 위 목록에 더해:

| **아르**(에이전트) | 05-design §0.5 전 화면 공통 진입점 · ADR-0009 "768px 이하는 덮는 오버레이" | 오버레이라 전체 화면 시트다. 진입점은 탭 화면에서 오른쪽 아래 버튼, 파고든 화면(상세)에서는 하단이 [단계 변경] 자리라 **상단 바 아바타**로 옮겼다. §1 AI 규약(앰버 점선 = 제안 / 잎초록 실선 = 사람 확정)을 그대로 지킨다 — 제안 카드의 승인 버튼은 `POST /agent/confirm` 자리이고 **지금은 잠겨 있다** |
| **설정** | 배포판 웹 설정 4탭 | 탭이 가로 스크롤이다. **내 계정 탭만 잠금이 풀렸다**(2026-09-03) — `PATCH /auth/me` 로 이름·비밀번호를 바꾼다. 그 API 가 받는 것이 둘뿐이라(`MeUpdate`) **이메일·역할은 잠긴 채**다: 로그인 식별자와 권한이라 본인이 바꿀 것이 아니다. 나머지 세 탭은 아직 잠겨 있고, 잠긴 이유를 화면에 적어 둔다. **비밀번호 오타의 401 을 만료로 보면 안 된다** — `authExpiryOn401: false` 를 안 주면 오타 한 번에 토큰이 지워져 로그아웃된다 |
| **지원자 상세** | 앱 UI 초안 2026-09-01 (배포판 웹 상세 패널 기준) | 전형 레일 → **아르의 요약** → 지원 정보 → 메일 → 시스템 → 메모 → 단계 이력 순. 아르의 요약은 `ai_summary` 의 **JSON 을 웹과 같은 규격으로 파서** 요지 / 강점 / 확인 필요로 그린다(면접 확인 포인트는 값이 와도 안 그린다 — 05-design §0.5). 시안이 항목마다 카드 한 장으로 바꿨던 지원 정보는 필드가 7개로 늘면서 **한 카드 안 목록**으로 되돌렸다 |

| **공고 등록·수정** | 웹 `Postings.tsx` 의 `[+]` | **웹에는 둘 다 없다** — `[+]` 는 핸들러가 없고 수정 화면도 없다. 공고를 만들고 고칠 수 있는 곳은 지금 앱뿐이다(2026-09-03). 한 화면이 둘을 다 한다(칸이 셋으로 같다): 등록은 `POST /postings`, 수정은 `PATCH /postings/{id}`. 진입점은 등록이 공고 탭 `[+]`, 수정이 **그 공고의 지원자 화면** `[✎]` — 고칠 대상이 이미 화면에 떠 있는 자리다. **삭제도 여기 붙였다**(2026-09-03, 아래 절). `description` 은 앱에 칸이 없어 안 보낸다: 안 보내면 서버가 안 건드리므로 웹에서 적은 것이 지워지지 않는다 |

| **평가 쓰기** | 웹 `Evaluations.tsx` 의 오른쪽 패널 | 점수 1~5 버튼·코멘트(선택)는 웹과 같다. 375px 엔 "오른쪽" 이 없어 **평가 화면 위쪽 `내 평가` 블록**에 둔다(§9). **중복을 앱이 막는다**: 서버도 웹도 같은 사람이 여러 번 평가하는 것을 안 막아 그냥 POST 하면 한 사람이 여러 줄을 남기고 **평균과 "n명이 평가함" 이 둘 다 틀어진다**. 내가 쓴 것이 있으면 `PATCH /evaluations/{id}` 로 고친다 — 서버에 "내 것만 고칠 수 있다" 는 검사가 이미 있는데(`evaluator_id != user.id`) 웹이 안 쓰고 있었다. 내 것 찾기는 `AppUser.id` 와 `evaluator_id` 비교라 추가 요청이 없다. **서버가 평가자 이름을 안 줘서**(`EvaluationOut` 은 `evaluator_id` 뿐) 목록에 붙는 이름은 내 것의 `나` 하나뿐이다 |

| **메일 발송** | 웹 `ApplicantPanel.tsx` 의 메일 절 | 웹과 같은 **3단계**: 프리셋 → 프리필 편집 → **확인**. 프리셋 넷과 치환은 웹 그대로고 **치환은 서버가 한다**(`GET .../emails/preview?stage=`) — 화면이 채우면 미리보기와 실제가 갈린다. 웹은 오른쪽 패널 안에서 펴지지만 앱은 **별도 화면**이다(375px 에 제목 칸 + 본문 10줄을 상세에 끼우면 그 아래가 다 밀린다). 확인 시트에 **받는 사람 이름**을 적는 것이 웹과 다른 점 — 폰은 목록에서 잘못 눌러 들어오기 쉽고, 그때 누구에게 가는지가 화면에 없으면 안 걸러진다. **주소는 안 적는다**: 수신자는 서버가 `application.email` 로 고정해 앱이 틀릴 수가 없으니 띄워도 막을 실수가 없고, 지원자 개인 이메일을 덮어씌우는 시트에 올릴 이유가 그만큼 약하다(웹도 안 띄운다) |

**큐 8 이 2026-09-03 에 다 끝났다 — 목데이터로 남은 화면이 없다.**

- **3단계(쓰기)**: 메모 · 단계 변경 · 공고 등록/수정 · 평가 · 이름/비밀번호 · 메일 발송
- **4단계(읽기)**: 이력서 열기 · 캘린더 · 메일 이력 · 단계 이력 · 설정 3탭 · 대시보드 · 평가 대기 큐 · 통합 검색
- **5단계(아르)**: `POST /agent/chat` + `POST /agent/confirm`

**대시보드 전형 현황은 진행중 공고만 센다**(2026-09-03 결정). 마감된 공고 지원자가 숫자를 먹으면 "지금 뭘 해야 하나" 가 안 읽힌다. 공고 목록이 이미 공고별 단계 인원과 지원자를 주므로 **요청이 하나도 더 들지 않는다** — 오히려 웹 방식(단계마다 검색 4번)보다 싸다. 일정 칩은 웹처럼 **화면에 이름이 뜨는 몇 명만** 병렬로 묻고, **404 는 오류가 아니라 "아직 제안을 안 보냈다"** 다.

**통합 검색**: `offset` 페이지네이션(웹과 같다) + 폰이라 페이지 번호 대신 **[더 보기]** 로 이어 붙인다. 타자마다 보내지 않게 **300ms 디바운스** — 로컬 필터였을 땐 공짜였지만 서버가 되면 글자 하나에 왕복 하나다. **서버 `q` 는 이름·이메일만 본다**(`search.py:120`) — placeholder 가 약속한 공고명 검색은 `posting_id` 로 좁힌다(웹도 같은 이유로 따로 처리).

**아르**: 대화 이력은 **서버가 저장하지 않아** 화면이 들고 매번 같이 보낸다(웹도 같다) — 시트를 닫으면 대화가 사라지는 것은 그래서다. **쓰기 도구는 아르가 스스로 실행하지 않는다**: 서버가 `pending_action` 을 주면 **앰버 점선 확인 카드**를 띄우고 사람이 눌러야 `POST /agent/confirm` 이 돈다(05-design §1 이 앰버를 쓰라고 한 자리 — 이 화면 문서가 예고해 둔 대로 되살렸다). 목데이터 시절의 명단 카드는 **서버 응답에 그런 구조가 없어**(글 + 도구 호출뿐) 안 그린다.

**메일은 이 앱에서 유일하게 되돌릴 수 없는 동작이다.** 큐에 쌓이는 것이 아니라 SES 로 실제 발송된다(`backend/app/worker.py`). 그래서 [보내기] 만으로는 안 나가고 확인 시트를 반드시 거친다.

**평가는 지울 수 없다** — 서버에 `DELETE /evaluations/{id}` 가 없다. 고칠 수만 있다. `member` 는 자기에게 배정된 지원자만 쓸 수 있어(`assert_can_evaluate`, ADR-0017) 배정 안 된 건에는 403 이 온다 — 서버 문구를 그대로 띄운다.

**공고 삭제 — 앱에 붙였다 (2026-09-03).** 배포된 `DELETE /postings/{id}` 를 부르는 곳이 웹에도 앱에도 없어 잘못 만든 공고를 지울 방법이 아무 데도 없었다. 자리는 **공고 수정 화면 맨 아래**, 저장 바 바깥이다 — 같은 줄에 두면 손가락이 스치고, 스크롤 끝이라는 위치가 "여기서 끝"이라는 뜻도 된다. **확인 시트를 한 번 거친다**(메일 발송과 같은 부류다): 시트에 공고명을 적어 목록에서 잘못 눌러 들어온 경우를 거른다.

**지원자 수를 앱이 세지 않는다.** 서버가 지원서 딸린 공고를 **409 로 막고**(`backend/app/api/postings.py` — `applications.job_posting_id` 에 ondelete 규칙이 없어 함께 지우려면 스키마 변경이다), 그 문구에 **몇 건이 걸렸는지와 "먼저 공고를 마감하세요"** 가 다 들어 있다. 화면이 들고 있는 인원은 받아 온 시점의 값이라 그 사이 지원자가 들어오면 앱은 "지울 수 있다"고 보여 주고 서버는 막는다 — 세는 쪽을 하나로 두고 서버 문구를 그대로 띄운다. 그래서 여기서 실제로 지워지는 것은 **아무도 지원하지 않은 공고뿐**이다. 지웠으면 그 공고의 지원자 화면도 함께 닫는다(없어진 공고의 목록이다).

**웹에는 여전히 삭제가 없다** — 팀에 올릴 것.

화면 설계 기준: [planning/00_summary_ko.md](../04_planning/00_summary_ko.md) 8장 + `frontend/mockups/mockup-mobile.html` + **모바일 시안(2026-08-28, 프론트 오너 작성)** + **앱 UI 초안(2026-09-01, 앱 오너 작성 — 배포된 웹 + 05-design 기준)**. 목업에 없던 5건(단계 변경 UI · 단계 이력 · 평가 목록 · 퍼널 바 배치 · 공고 리스트)을 시안이 채웠고, 그 과정에서 기존 화면의 치수도 함께 정해졌다 — **뒤에 온 것을 따른다: 목업 < 시안 < 앱 UI 초안.** 다만 **셋 중 무엇이든 05-design 과 어긋나면 05-design 이 이긴다** (초안이 `8월 28일 (금)` 로 그렸던 날짜를 §2 표기 통일에 맞춰 `2026.09.01` 로, 월 그리드 캘린더를 주간 스트립으로 바꾼 것이 그 사례다).

**제외** — 지원 폼(지원자용 외부 링크는 웹 전용) · 칸반(모바일 금지 원칙) · 앱 내 푸시 알림 G7(△ 여유 — 하게 되면 별도 합의) · 스토어 배포(데모는 Android APK 직접 전달, 여유 시 Play 내부 테스트 트랙까지) · **팀 기기 전원 APK 배포**(2026-09-02 계획에서 뺌 — APK 는 필요할 때 뽑아 전달하면 되고, 기기마다 설치를 확인하는 것 자체를 마일스톤으로 둘 이유가 없다. 필요해지면 그때 다시 넣는다) · **iOS 실기기 시연**(Mac 부재로 빌드 불가 — ADR-0010).

## 7. 리스크

- **iOS 빌드 검증 불가** (Mac 없음) → 호환은 코드 규율로만 관리한다: iOS 지원 플러그인만 사용, `Platform.isAndroid` 분기 금지, `flutter analyze` 무경고. **"iOS도 된다"고 말하지 않는다** (ADR-0010).
- **Dart·Flutter 첫 사용 + 팀 내 사용자 0명** → 막히면 전부 혼자 푼다. SDK·`flutter doctor`·실기기 구동은 08/26 에 통과했으므로(#114) 남은 위험은 언어·프레임워크 자체다. 하루 안에 안 풀리면 팀 채널에 올린다.
- **개인 기기·개발 환경 편차** → M1에서 팀 Android 기기 전원에 APK 설치를 먼저 확인하고, 안 되는 기기는 데모 대상에서 뺀다. QR 즉시 반영이 없으므로 **배포 확인을 주 1회로 정기화**한다.
- **웹과 룩이 어긋남** → 토큰을 코드로 이식하고(임의 색 금지), 완료 기준에 목업·시안 대조 포함. **시안에 없는 값이 필요하면 만들지 말고 묻는다**(05-design §12) — 목업에 없던 5건이 그렇게 해결됐다.
- **백엔드 지연** → M1이 전부 API 무관. 전환기 큐로 본인이 선행을 만든다.

- **같은 API로 웹·앱 두 클라이언트** — 클라이언트 추가가 서버 변경 0으로 끝났는가, 아니면 무엇이 부족해 무엇을 바꿨는가
- 모바일에서 칸반을 버리고 리스트+단계 변경 버튼으로 간 **UX 재설계 근거** (기획 §2-3을 본인 언어로)

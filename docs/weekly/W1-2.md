> **발생** 08/24 · **요청** 팀장 · **담당** 팀장 + 팀원3 · **분량** ±0점 (교체)
> **본 계획서**: [W1.md](W1.md) — **이 문서는 W1을 대체하지 않는다.** 아래 3·4항에 적힌 것만 바뀌고 나머지는 W1 그대로다.

## 왜 생겼나

4주차를 **완성된 것을 다듬는 기간**으로 비워두기로 했다. 그러면 남는 개발 기간이 이렇게 된다.

| | |
|---|---|
| 전체 | 4주 · 실작업일 20일 |
| 1주차 | 정적 목업 — **기능 완료 0개** |
| 4주차 | 유지보수·안정화 — **신규 기능 0개** |
| **실제 개발 기간** | **2주 · 10일** |

10일에 필수 기능 전부. 5명이면 50 사람-일이고 **기능당 1.9 사람-일**이다.
D2 칸반 · D3 드래그 · G2 SQS 워커 · G3 재시도 · H2 인덱스 튜닝 · F1 S3 presigned · A3 권한 · J2 AWS 배포 — 이것들은 하나에 2~3일씩 걸린다. **평균 1.9일로는 안 된다.**

> **확인된 사실 하나**: 문서들이 필수 기능을 **23개**라고 적고 있지만, [planning/00_summary_ko.md](../planning/00_summary_ko.md) 6장의 ●를 실제로 세면 **27개**다. (전체도 "73개"라 적혀 있으나 절 소계를 더하면 80개.) 일정을 23 기준으로 잡았다면 처음부터 17% 모자란 계획이었다. **이 카운트 정정은 별도 PR로 처리한다.**

1주차에서 되찾을 수 있는 시간은 **ERD 확정을 앞당기는 것** 하나뿐이다. 기획 [§2-5 "최대 위험 구간 — 1주차"](../planning/00_summary_ko.md)도 원래 *"1주차 2일차까지 테이블 정의서를 확정하라"*고 못박고 있었다.

## 할 일

### 1. ERD 확정 게이트를 앞당긴다 — 팀장

**바뀐 조건**: 목업 8장 전부 완성 → **C1 지원폼 · E1 평가현황 두 장의 PR이 머지된 직후** (목표 Day 3, 늦어도 Day 4)

- [ ] C1 · E1 머지되면 그 화면에 실제로 쓰인 필드로 [01-erd.md](../01-erd.md) 검증
- [ ] 문서 상단 상태 줄을 `확정 vX.X · 날짜`로 교체

**근거 — 8장이 다 필요하지 않다.**

- `frontend/mockups/mockup.html` 645줄은 **이미 완성된 화면**이다. 지원자 목록 + 상세 패널 + 칸반이 다 들어 있다. "UI가 스펙이다"의 그 UI가 이미 존재한다.
- 추가 8장 중 **ERD에 새 컬럼을 요구하는 것은 C1(applications 전 필드)과 E1(evaluations)뿐**이다. 로그인 · 설정 · 공고목록 · 검색 · 대시보드 · 모바일은 기존 필드를 화면에 배치할 뿐 새 컬럼을 만들지 않는다.

**감수하는 위험**: 나중에 컬럼이 하나 더 필요해질 수 있다. [01-erd.md](../01-erd.md)가 각 표 비고에 확장 여지를 적어둬서 컬럼 추가는 감당 가능한 범위다. 대신 **테이블 추가·분리는 여전히 전원 합의**다.

### 2. 2주차 지시서를 주중에 쓴다 — 팀장

- [ ] Day 4~5에 2주차 지시서 작성, **금요일 배포**

ERD가 Day 3에 확정되면 지시서를 주말이 아니라 주중에 쓸 수 있다. **2주차 월요일 아침에 4명이 즉시 시작한다.** 원래 계획(Day 4~5 확정 → 주말 작성 → 월요일 배포)보다 팀 전체로 하루 이상을 번다. 이번 변경에서 가장 큰 소득이다.

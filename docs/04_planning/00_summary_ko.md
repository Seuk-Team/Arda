## 2. 확정된 결정과 근거

### 2-1. 쿠버네티스 제외

한 달 안에 K8s를 "굴렸다"고 말하려면 배포 전략(rolling / blue-green), 오토스케일링, 헬스체크 튜닝 중 최소 하나는 실제로 건드려야 한다. 서비스 기능까지 만들면서는 매니페스트 작성하고 파드 뜨는 수준이 한계이고, 그 정도는 면접에서 파고들면 방어가 안 되는 항목이 된다.

대신 **Docker + AWS + GitHub Actions CI/CD**까지를 목표로 잡는다. 신입 기준으로 충분한 셀링 포인트다.

### 2-2. 역할 분배 기준 = 작업량 5등분이 아님

초반 1주는 백엔드가 스키마를 못 내면 나머지 4명이 놀고, 마지막 주는 프론트에 일이 몰린다. 그래서 두 가지를 기준으로 나눴다.

- 각자 놀지 않는 구간을 만들 것
- 각자 면접에서 말할 거리를 하나씩 가질 것

CRUD 화면을 1인 1개씩 나눠 갖는 방식은 다섯 명이 이력서에 똑같은 한 줄을 쓰게 되므로 배제했다.

### 2-3. 모바일은 칸반이 아니라 리스트

PC의 칸반 보드를 모바일에서 그대로 축소하면 컬럼이 좁아져 사용 불가가 된다. 모바일에서는 단계 탭 + 리스트로 가고, 단계 이동은 드래그 대신 상세 화면의 "단계 변경" 버튼으로 처리한다.

### 2-4. AI가 붙인 것과 사람이 확정한 것을 색으로 구분

프로토타입의 디자인 원칙. **앰버 점선 = AI가 제안한 것 / 청록 실선 = 사람이 확정한 것.** AI 점수 박스에는 "확정은 담당자가 합니다"가 항상 붙는다. 설계 원칙이 화면에서 바로 읽히도록 한 장치다.

### 2-5. 최대 위험 구간 — 1주차

A가 스키마를 못 내면 B · C · D가 전부 대기 상태가 된다. **1주차 2일차까지 테이블 정의서를 확정하고, 이후 스키마 변경은 전원 합의로만 진행한다.** 이 규칙이 없으면 3주차에 스키마 바꾸느라 하루가 통째로 날아간다.

## 3. 기능 범위

**포함**

- 채용 공고 등록 · 관리
- 지원서 제출 + 이력서 업로드

- 외부 채용사이트 연동
- 통계 대시보드 (여유가 생기면 여기부터 착수)

## 4. 역할 분배

> 이미지 `01_역할분배_일정.png`의 내용입니다.

| | 담당 | 핵심 작업 | 면접에서 말할 것 |
|---|---|---|---|
| **A** | 도메인 백엔드 | 공고 · 지원자 CRUD / 단계 전환 로직 / 이력 기록 테이블 | 상태 전환 규칙을 DB와 코드 중 어디서 강제했는가 |
| **B** | 검색 · 데이터 | 검색 · 필터 API / 인덱스 설계 / 더미 10만건 생성 | 느린 쿼리를 어떻게 찾아냈고 인덱스로 얼마나 줄였는가 |
| **C** | 파일 · 알림 | S3 presigned 업로드 / SES 메일 발송 / SQS 비동기 큐 | 파일 업로드가 왜 API 서버를 거치면 안 되는가 |
| **D** | 프론트엔드 | 칸반 보드 UI / 지원 폼 · 상세화면 / Vercel 배포 | 드래그 실패 시 낙관적 업데이트를 어떻게 롤백했는가 |
| **E** | 인프라 · 인증 | Docker · AWS 배포 / 로그인 · 권한 분리 / CI/CD · 모니터링 | 배포 파이프라인과 권한 모델을 어떻게 설계했는가 |

**전원 공통**: 자기 담당 API 문서화, 테스트 코드, 발표 자료 본인 파트.

### 왜 이렇게 나눴는가

- **B(검색)를 독립 역할로 뺀 것이 핵심.** 보통 검색은 A가 겸하는데 그러면 A가 과부하고 B 자리가 애매해진다. 지원자 10만 건을 더미로 넣고 검색을 튜닝하는 것은 그 자체로 한 달짜리 일이며, SQL을 제대로 쓰는 유일한 자리다.
- **C(파일 · 알림)는 AWS를 실제로 쓰는 유일한 자리.** S3 presigned URL과 SQS 비동기 메일이 없으면 AWS는 그냥 EC2 한 대가 되고, 발표에서 AWS를 썼다고 말할 근거가 약해진다.
- **E가 인증까지 가져가는 이유**는 인프라만 맡으면 첫 주에 몰아서 끝나고 나머지 3주가 비기 때문이다. 인증 · 권한(채용담당자 / 면접관 분리)은 중간에 계속 손이 가서 부하가 고르게 퍼진다.

## 7. 화면 설계 — PC

> 이미지 `03_목업_PC.png`의 내용입니다.

### 화면 ① 지원자 칸반 보드 (메인)

- **좌측 사이드바**: 로고, 메뉴(대시보드 / 지원자 / 채용 공고 / 평가 현황 / 설정), 하단에 로그인 사용자와 권한 표시
- **상단 헤더**: 공고 제목, 진행 상태 뱃지, 마감 D-day, 총 지원자 수
- **퍼널 레일**: 5단계가 하나의 가로 막대로 이어지고, 각 단계의 폭이 인원수에 비례. 누르면 그 단계만 보기
- **툴바**: 검색창(이름 · 학교 · 기술스택), 기술 필터 칩, 신입 필터, AI 서류 검토 버튼, 에이전트 호출 버튼
- **칸반 컬럼 5개**: 지원 접수 / 서류 검토 / 면접 / 최종 합격 / 불합격. 컬럼 헤더에 단계 색 막대와 인원수
- **지원자 카드**: 이름, 첨부 아이콘, 학력 · 경력, 기술 태그, 평가 별점, AI 점수 뱃지. 카드 왼쪽에 단계 색 스트립
- **드래그 드롭존**: 빈 컬럼에 "카드를 여기로 옮기세요" 안내

### 화면 ② 지원자 상세

- **헤더**: 목록으로 돌아가기, 지원자명, 현재 단계 뱃지, 지원일 · 공고명, 우측에 단계 변경 / 합격 처리 버튼
- **좌측 패널**: 지원 정보(연락처 · 이메일 · 학력 · 경력 · 기술), 이력서 PDF 첨부 카드(S3 저장 · presigned URL 다운로드), 자기소개서
- **우측 패널**: 단계 이력 타임라인(누가 언제 어느 단계로), 평가 코멘트 목록과 평균 점수, 하단에 평가 입력창

## 9. 동작 프로토타입

`ats-prototype.html` — 브라우저로 열면 바로 동작한다. 설치 불필요.

**실제로 동작하는 것**

- 칸반 카드 드래그로 단계 이동 → 이력 기록 + 메일 발송 알림
- 검색어 · 기술 칩 · 신입 필터가 실제로 목록을 거름
- 퍼널 레일: 막대 폭이 단계별 인원 비율, 클릭 시 해당 단계만 표시
- 카드 클릭 → 상세 패널, 별점 + 코멘트 등록 시 평균 재계산
- AI 서류 검토: 점수가 순차적으로 채워지며 정렬. **확정은 사람이 눌러야 실행됨**
- 에이전트 콘솔 (⌘K): 문장을 넣으면 검색 → 필터 → 단계 변경 → 메일 초안까지 4단계 실행 로그
- 모바일: 단계 탭 필터, 상세, 단계 변경 / 지원 폼 업로드 진행률

**디자인 원칙**: 앰버 점선 = AI가 제안한 것, 청록 실선 = 사람이 확정한 것.

## 10. 강사 피드백 4건에 대한 팀 입장

### ① AI 서류 자동 판정 → **받되 수정**

AI가 이력서를 읽고 요건 매칭 · 점수화 · 랭킹까지 수행한다. 단, **최종 합불은 사람이 확정**하는 구조로 간다.

- EU AI Act는 채용을 고위험으로 분류해 인적 감독을 요구함
- 미국 EEOC도 자동 스크리닝이 장애인을 걸러내면 ADA 위반이 될 수 있다고 경고
- 사람 검토 없는 자동 탈락은 심사에서 바로 지적당하는 지점

발표 효과는 동일하다(수십 명이 몇 초 만에 점수순 정렬). 오히려 "왜 사람 확정을 남겼나"에 답할 거리가 생긴다.

### ② 실시간 표정분석 → **제외**

업계가 이미 폐기한 기능이다.

- HireVue(이 분야 최대 업체)가 2021년 3월 표정분석 중단. 독립 감사 결과 표정 데이터의 직무성과 예측 기여도가 0.25% 미만
- 얼굴 움직임만으로 감정을 추론하기 어렵다는 것이 학계 정리 (Barrett 외, 2019)
- 안면마비 · 자폐 · 시선 패턴 차이가 있는 지원자를 결함으로 점수화하는 차별 위험이 문서화됨

추가로 "긴장 = 부적합"이라는 전제 자체가 검증된 바 없다. 임계값 근거를 질문받으면 방어가 불가능하다.

**판단 기준**: "측정할 수 있다"와 "쓸모가 있다"는 다른 문제다. 긴장도 숫자가 나온 뒤 면접관이 무엇을 하는지에 답이 없으면, 그것은 의사결정에 쓰이지 않는 지표다.

발표에서는 이렇게 말한다 — *"표정분석은 구현 난이도 때문이 아니라 의사결정에 쓸 수 없어서 뺐습니다. HireVue도 같은 이유로 2021년에 이 기능을 내렸습니다."* "못 만들어서 뺐다"와 "안 만드는 게 맞다고 판단해서 뺐다"는 완전히 다른 인상을 준다.

### ③ 지원자 SNS 크롤링 → **제외**

윤리 이전에 법 문제다.

- 채용절차법 제4조의3, 개인정보보호법 제15조가 구직자 개인정보 수집을 직무 관련 최소한으로 제한
- 평판 조회조차 본인 서면 동의가 필요하다는 것이 실무 해석
- 인스타그램 · 트위터 ToS 위반이 별도로 발생

동의 없이 수집해 성격 · 성실성을 판정하는 기능은 시연 자체가 리스크다.

### ④ 실시간 화상면접 → **일정상 제외**

기능 자체에는 문제가 없으나 범위 문제다. 3인 이상 동시 접속은 시그널링 서버 + TURN + SFU까지 필요하고, 이 항목 하나가 인력 1명의 4주를 소모한다. 현재 5인 배분에서 차출할 여력이 없다.

### 원칙

**버튼으로 되는 일은 버튼으로 한다. 에이전트는 버튼으로 안 되는 작업에만 쓴다.** 반대로 하면 "그거 버튼이면 되는 거 아니냐"는 질문에 답할 수 없다.

### ① 이력서 비정형 → 정형 변환 (가장 정당한 자리)

제각각인 PDF 이력서에서 경력 연차 · 기술스택 · 학력을 구조화 필드로 추출한다. 버튼으로는 애초에 불가능한 작업이고, 이게 되어야 B가 만드는 검색 · 필터가 실제로 동작한다.

### ② 도구 호출형 에이전트

예시 명령:

> "이번 공고에서 Python 2년 이상 + AWS 경험자 추려서 서류합격 처리하고 면접 안내 메일 초안 써줘"

검색 + 필터 + 상태 변경 + 문서 생성이 한 문장에 묶인다. 버튼으로 하면 화면 4개를 오가야 하는 작업이다. 이것이 에이전트가 도구를 순차 호출하는 교과서적 시나리오다.

**메일은 초안까지만 만들고 발송은 사람이 확정한다.**

### ③ 서류 기반 RAG 질의응답

지원자 정보에 대한 자연어 질의. 단독으로는 변별력이 약하므로 ① ②의 보조로 배치한다.

## 12. 음성 인식 설계

### 12-1. 선택지는 이지선다가 아니다

음성 기능은 세 층으로 쪼개진다. **입력(STT) / 판단(에이전트) / 출력(TTS)** 이 각각 독립이다.

| 방식 | 구조 |
|---|---|
| speech-to-speech (실시간 음성 API) | 세 층을 벤더가 통째로 가져감 |
| **STT + 기존 텍스트 에이전트** | 입력만 붙이고 판단은 우리 코드 ← 채택 |
| STT + 에이전트 + TTS | 위에 음성 출력만 추가 (TTS는 API 한 줄) |

### 12-2. speech-to-speech를 쓰지 않는 이유

"그냥 API 호출이라 기술이 없다"보다 결정적인 문제가 있다. **tool calling이 벤더 런타임 안으로 들어간다.**

우리 에이전트의 핵심 — 문장을 받아 검색 · 필터 · 상태변경 도구를 순서대로 호출하는 부분 — 이 벤더 세션 안에서 일어난다. 우리는 도구 스펙만 등록하고 결과를 돌려주는 껍데기가 된다. **음성을 붙이려다 에이전트를 뺏기는 구조**이고, 포트폴리오 관점에서 최악이다. 발표는 화려한데 코드에 우리 몫이 없다.

비용도 참고 — 실시간 음성 모델은 오디오 입력 100만 토큰당 $32, 출력 $64 수준이며 대화 1분당 약 $0.05, 캐싱 없이 실제 에이전트로 돌리면 분당 $0.18~$0.46까지 올라간다. 데모에서는 무시할 수준이지만 "기업이 이걸 왜 쓰냐"는 질문이 여기서 다시 걸린다.

### 12-3. 기술적 알맹이는 STT가 아니라 그 다음에 있다

Whisper를 붙이는 것 자체도 그냥 호출이다. **기술은 전사된 텍스트와 도구 호출 사이에 있다.**

한국어 음성 명령에서 실제로 깨지는 지점:

```
발화: "김도현씨 면접으로 옮겨줘"
전사: "김도 현씨 면접으로 옮겨줘"      ← 띄어쓰기 붕괴
전사: "김도현 씨 면접으로 옮겨 줘"      ← 조사 "씨" 처리

발화: "파이썬 경력 이년 이상"
전사: "파이썬 경력 2년 이상" / "이년"   ← 숫자 표기 불일치

발화: "패스트API"
전사: "패스트 에이피아이" / "fast API"  ← 기술 용어 음차
```

이를 처리하는 **엔티티 해석(entity resolution) 레이어**가 실제 구현 대상이다.

- 지원자 이름을 DB에서 유사도 매칭 (편집 거리 또는 초성 매칭) → 후보가 여럿이면 되묻기
- 기술 스택 사전으로 음차 표기 정규화 (`패스트에이피아이` → `FastAPI`)
- 한글 수사 → 숫자 변환 (`이년` → `2`)
- **파괴적 작업은 반드시 확인 단계**: "김도현을 불합격으로 옮길까요?" — 음성 오인식 한 번으로 사람의 채용 결과가 바뀌면 안 된다

"Whisper 붙였습니다"는 3초면 끝나지만, "음성 인식 오류가 도구 호출로 전파되는 것을 어떻게 막았는가"는 10분 설명할 수 있다.

### 12-4. 로컬 vs API → API 채택

성능이 아니라 **배포** 때문이다.

로컬(faster-whisper)은 개인 GPU에서는 잘 돈다. 그러나 이 프로젝트는 AWS 배포가 필수 요건이다. GPU 인스턴스를 띄우면 비용이 튀고, CPU로 돌리면 지연이 심해 데모가 답답해진다. 결국 "내 컴퓨터에서만 되는 기능"이 되고, 발표 당일 노트북이 죽으면 같이 죽는다.

로컬이 정당해지는 경우는 하나뿐이다 — **비용 / 프라이버시를 설계 근거로 내세울 때.** 지원자 음성이 외부로 나가면 안 된다는 논리는 실제로 성립한다. 다만 그러려면 GPU 인스턴스 비용 계산까지 발표에 포함해야 논리가 닫힌다.

### 12-5. 결론

**Whisper API로 STT → 기존 텍스트 에이전트 → 텍스트 응답.** TTS는 여유가 되면 한 줄 추가한다.

응답을 텍스트로 두는 실무적 이유도 있다. 지원자 목록 12명을 음성으로 읽어주면 아무도 듣지 않는다. **조회 결과는 화면이 이기고, 명령은 음성이 이긴다.** 이 구분 자체가 설계 판단이며 발표에서 말할 수 있는 근거다.

**미결정 사항**: 음성 입력을 어디에 붙일지. 담당자용 에이전트 콘솔에만 붙일지, 다른 화면에도 넣을지에 따라 엔티티 해석 난이도가 크게 달라진다.

## 13. 저장소 · 문서 구조

5인 · 한 달 기준으로 **모노레포**를 권장한다.

```
ats/
├─ docs/
│  ├─ 00-overview.md        프로젝트 한 장 요약
│  ├─ 01-erd.md             테이블 정의서 (1주차 2일 마감)
│  ├─ 02-api.md             엔드포인트 목록
│  ├─ 03-conventions.md     브랜치 · 커밋 · 코드 규칙
│  └─ adr/                  결정 기록
├─ backend/
├─ frontend/
├─ infra/
└─ README.md
```

**모노레포인 이유**

- PR에서 프론트 · 백엔드 변경을 함께 볼 수 있다
- 스키마 변경 시 양쪽을 한 커밋에 묶을 수 있다
- 평가자가 저장소 하나만 보면 된다

**`docs/adr/`을 따로 두는 이유**

지금까지 정한 결정들(K8s 제외, 표정분석 제외, AI는 추천만, 음성은 STT만)을 문서로 남겨두면 **면접에서 그대로 꺼낼 수 있는 자산**이 된다. "왜 그 기술을 안 썼냐"는 질문에 커밋 히스토리로 답하는 팀은 거의 없다.

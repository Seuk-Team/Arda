# 03. 협업 규칙 (브랜치 · 커밋 · PR · 이슈)

## 원칙

- **main은 항상 동작하는 상태.** main 직접 커밋 금지 (팀장 포함).
- 모든 작업은 **이슈(기능 번호) → 브랜치 → PR → 리뷰 → 머지**. 누가 리뷰하는지는 아래 리뷰 절 — 도메인 오너제([ADR-0007](../03_decision/0007-도메인-오너제-전환.md), [04-team.md](04-team.md)) 기준이다.

## 이슈

- 작업 단위 = 기능 번호 하나 (A1~J11, [planning/00_summary_ko.md](../04_planning/00_summary_ko.md) 6장).
- 제목: `[D3] 드래그로 단계 이동`. 본문에는 해당 지시서(`docs/02_tasks/`) 링크.

## 브랜치

- `feat/<기능번호>-<슬러그>` — 예: `feat/j7-dummy-generator`
- `fix/<기능번호>-<슬러그>` / `docs/<슬러그>`
- 브랜치는 머지 후 삭제.

## 커밋

- 형식: `<type>(<기능번호>): <요약>` — 예: `feat(J7): 더미 지원서 10만 건 생성기`
- type: `feat` `fix` `docs` `test` `chore` `refactor`
- 요약은 한국어로, 무엇이 왜 바뀌었는지.

## PR

- 하나의 PR = 하나의 기능 번호(또는 로드맵 큐 항목 하나). 크면 쪼갠다.
- 본문 필수 항목: **무엇을 했나 / 어떻게 확인했나(실행·테스트 결과) / 스키마·API 변경 여부(있으면 안 됨 — 있다면 먼저 합의)**
- 리뷰 지적은 해당 PR에서 해결하고 머지한다.

## 리뷰 — 누가 승인하고 누가 머지하나

변경 파일 기준으로 세 단계다. **위가 아래에 우선한다.**

| 이 파일이 섞였으면 | 승인 | 근거 |
|---|---|---|
| ① **인터페이스·공용**: `docs/00_overview/01-erd.md` · `docs/00_overview/02-api.md` · `backend/app/models.py` · 최상위 `docs/0*.md` · `CLAUDE.md` · `README.md` · `.github/` | **팀장** (스키마는 확정 후 전원 합의가 선행) | 전원이 딛는 계약 |
| ② **다른 도메인의 파일** (예: 에이전트 PR에 `frontend/` 파일 포함) | **그 도메인 오너** | 폴더 경계 = [04-team.md](04-team.md) 표 |
| ③ **자기 도메인 파일만** | **없음 — 오너가 스스로 머지** | 오너 책임제 |

③의 셀프 머지 조건: PR 본문에 실행·테스트 결과가 있고, CI가 생기면(J4) CI 통과. 조건을 못 채우면 머지하지 않는다.

- 예외: `backend/app/main.py`의 `include_router` 한 줄 추가는 ②로 치지 않는다 — 기존 규칙대로 한 줄만 추가하고, 충돌 나면 양쪽 줄을 다 남긴다.
- 자기 도메인 로드맵(`docs/01_role/<자기 도메인>.md`)의 큐·진행 상태 갱신은 ①이 아니라 ③이다. 단 범위·마일스톤 변경은 팀장 합의.
- CODEOWNERS는 **리뷰어 자동 지정용**이다 — 승인 강제는 GitHub 설정이 아니라 이 표의 규칙으로 한다. 규칙을 어긴 머지가 발견되면 revert가 기본값.

## 스키마 · API 변경

- [01-erd.md](01-erd.md) 확정 후 변경은 **전원 합의로만**. 합의 → 문서 갱신 → 마이그레이션 → 코드 순서.
- API 추가·변경은 [02-api.md](02-api.md) 갱신을 같은 PR에 포함한다.

## 환경변수

- 시크릿은 `.env`(git 제외). 키 이름은 `.env.example`에 반영해 팀원이 알 수 있게 한다.

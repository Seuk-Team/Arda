# 03. 협업 규칙 (커밋 · push · 사후 공지)

> **2026-08-28 개정**: 사람 리뷰·승인 게이트 전면 폐지 — 전원 main 직접 push. 배경: 전원이 Claude로 작업해 사람 검수가 형식화됨. 이전 규칙(이슈→브랜치→PR→리뷰)은 git 이력 참조.

## 원칙

- **전원 main에 바로 push한다. 사람 승인 게이트는 없다.** 각자 Claude가 검증(실행·테스트)까지 마친 상태로 push하는 것을 전제로 한다.
- **main은 항상 동작하는 상태** — 이 책임이 리뷰어에서 push하는 사람에게 넘어왔다. 깨진 main을 발견한 사람은 묻지 않고 고치거나(fix-forward) revert한다.
- CI(J4)가 생기면 **빨간불 = 다른 작업보다 우선 수정.**
- 이의는 사후에: 변경이 마음에 안 들면 팀 채널에서 얘기하고, 합의가 안 되면 revert가 기본값.

## push 절차

1. `git pull --rebase origin main`
2. 자기 파트 실행/테스트 — 결과는 커밋 메시지에 한 줄
3. push. 충돌하면 rebase 후 재시도. force push는 금지(GitHub에서 차단됨).

## 커밋 — 리뷰가 없으므로 이력이 곧 기록이다

- 형식: `<type>(<기능번호|도메인>): <요약>` — 예: `feat(J7): 더미 지원서 10만 건 생성기`, `feat(front): React 라우팅 뼈대`
- type: `feat` `fix` `docs` `test` `chore` `refactor`. 요약은 한국어로, 무엇이 왜 바뀌었는지.

## 사후 공지가 필요한 변경 (팀 채널 한 줄)

| 변경 | 규칙 |
|---|---|
| **스키마** | **코드와 같은 커밋에서 [01-erd.md](01-erd.md) 갱신** + 공지. 문서 갱신 없는 스키마 변경 금지 — ERD가 전원의 계약이다 |

| **남의 도메인 폴더** | 커밋 메시지에 명시 + 공지. 큰 변경이면 직접 고치지 말고 이슈로 오너에게 |

## PR · 이슈 (선택)

- PR은 피드백을 받고 싶을 때만 연다. 승인 없이 셀프 머지.
- 이슈는 버그·요청·타 도메인 개선 제안 기록용으로 유지. 제목에 기능 번호.

## 주간 다이제스트

- 금요일에 그 주 커밋·변경 요약(Claude 생성)을 팀장이 훑는다. **검수가 아니라 파악용** — 여기서 나온 이견도 사후 커밋/revert로 처리한다.

## 환경변수

- 시크릿은 `.env`(git 제외). 키 이름은 `.env.example`에 반영해 팀원이 알 수 있게 한다.

관계 요약 — 소유 스파인

실제 소유 관계는 한 줄기다: job_postings → applications → 자식 6개. users 는 이 줄기에 얹히지 않고 5개 테이블이 행위자로 참조하므로, 선으로 긋지 않고 각 테이블에 참조 배지로 표시했다.

소유 FK — 부모가 사라지면 자식도 의미를 잃는다 users 행위자 참조 — 작성자·변경자·배정자 1:N — 전부 일대다. 다대다 조인 테이블은 interviewer_assignments 하나뿐

ERD — 전체

까마귀발 표기. 부모 쪽 || = 정확히 하나, 자식 쪽 ○< = 0개 이상. 전부 1:N이고 다대다 조인 테이블은 interviewer_assignments 하나뿐이다. users 참조 5개는 선이 엉키지 않게 아래·오른쪽 여백으로 돌려 그렸다 — 얽혀 보이는 것은 users 가 소유 줄기에 끼어 있어서가 아니라, 다섯 군데에서 행위자로 불려서다.

지원서 — ★ 핵심 테이블 C1 · D1 · D6

확정 전에 정리할 것

초안이 확정으로 바뀌기 전에 답이 나와야 하는 항목. 아래 하나는 시점이 지나면 비용이 급격히 오른다.

미결 · 지금이 가장 싸다

files.s3_key → storage_path ?

S3를 쓰지 않고 로컬 디스크 저장으로 가면 s3_key 가 storage_path 로 바뀐다. 지금 바꾸면 한 줄이고, API·화면이 올라간 뒤면 그것들까지 따라간다.

합의 대상

검색 인덱스 (H1)

10만 건 튜닝용 추가 인덱스는 B 담당이 측정한 뒤 제안한다. 측정 없이 미리 넣지 않는다. 스키마 합의를 거쳐야 들어간다.

조건부 대공사

applicants 분리 (D11)

인재풀을 하게 되면 지원자 정보를 applications 에서 떼어내야 한다. 전원 합의 필요 — 이 문서에서 가장 큰 변경이다.

A5login_logs로그인 이력 — 별도 테이블로 추가. 기존 스키마 변경 없음
B4job_postings.deadline마감일 + 자동 마감
B6job_postings.public_token외부 접근용 공개 지원 링크
D8stage_history.reason불합격 사유 기록
E4evaluations.category평가 항목 분리 — 기술 / 커뮤니케이션 / 컬처핏
—stage: pending_review에이전트 정리 → 담당자 검수 플로우 도입 시 applied 앞에 추가. 검수 승인 시점에 공식 접수로 진입

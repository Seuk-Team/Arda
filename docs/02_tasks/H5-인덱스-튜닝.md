# [H1·H2] 인덱스 튜닝 — 전/후 측정

> 담당: 팀원2 · 역할 B(검색·데이터) · 브랜치: `feat/h5-index-tuning`
> **PR 단위**: 이 지시서 전체 = PR 1개

## 배경

**이 작업이 이 사람의 면접 카드다** ([04-team.md](../00_overview/04-team.md) B 역할: *"느린 쿼리를 어떻게 찾아냈고 인덱스로 얼마나 줄였는가"*).

핵심은 인덱스를 거는 게 아니라 **측정하는 것**이다. "인덱스를 걸었더니 빨라졌습니다"는 아무 말도 아니다. **어떤 쿼리가 몇 ms 였고, 왜 느렸고(실행 계획), 무엇을 걸었더니 몇 ms 가 됐는지**를 숫자로 남긴다.

먼저 재고, 계획을 읽고, 그 다음에 건다. **순서를 바꾸면 이 작업은 의미가 없다.**

## 선행 조건 — 없으면 중단

아래가 하나라도 아니면 **시작하지 말고 팀 채널에 알린다.** 없는 것을 상상해서 만들지 않는다.

- [ ] [H2 검색 · 필터 API](H2-검색-필터-API.md) PR이 머지돼 있다
- [ ] [J7 파트B](J7-더미데이터-생성기.md)로 **지원서 10만 건**이 DB 에 들어 있다
- [ ] `psql` 로 DB 에 붙을 수 있다

## 가장 중요한 규칙

- **[backend/app/models.py](../../backend/app/models.py)를 수정하지 않는다.** 컬럼이 부족해 보여도 추가하지 않는다. 멈추고 팀 채널에 묻는다.
- **[docs/00_overview/01-erd.md](../00_overview/01-erd.md)·[docs/00_overview/02-api.md](../00_overview/02-api.md)를 수정하지 않는다.** 공용 문서다.
- **인증·권한 코드를 넣지 않는다.** 인증은 팀장 담당(A1~A3)이고 아직 없다. 토큰 검사를 흉내 내면 나중에 팀장 것과 충돌한다. 사용자 id 가 필요한 자리는 `# TODO(A1): 토큰의 사용자로 채운다` 주석만 남긴다.
- **`main.py` 는 `include_router` 한 줄만** 건드린다. 그 파일의 다른 부분은 손대지 않는다.
- **인덱스를 먼저 걸지 않는다.** 측정 → 실행 계획 확인 → 인덱스 → 재측정 순서를 지킨다. 먼저 걸면 무엇이 좋아졌는지 말할 수 없다.
- **인덱스 추가는 스키마 변경이다.** [CLAUDE.md](../../CLAUDE.md) 규칙상 팀장 합의가 필요하다. 이 PR 은 **측정 결과와 제안**까지이고, `models.py` 는 팀장이 반영한다.
- **`models.py` 를 직접 고치지 않는다.** 제안 SQL 만 문서에 적는다.
- `EXPLAIN` 만 보지 말고 **`EXPLAIN ANALYZE`** 로 실제 실행 시간을 본다.

## 완료 조건

- [ ] `docs/perf-search.md` 신규 — **이 문서가 산출물이다**
- [ ] 측정 대상 쿼리 **4종**: ① 전체 목록 ② 이름 부분검색 ③ 단계 필터 ④ 공고+단계 복합
- [ ] 각 쿼리마다 **전 / 후** `EXPLAIN ANALYZE` 결과와 실행 시간(ms)을 표로
- [ ] 느린 이유를 실행 계획 용어로 설명 — `Seq Scan` 인가 `Index Scan` 인가, 행 추정치가 실제와 얼마나 차이 나는가
- [ ] 제안 인덱스와 **그것을 고른 이유**. 컬럼 순서가 왜 그 순서인지 포함
- [ ] **부분 검색(`%q%`)은 B-tree 인덱스가 안 먹는다**는 것을 확인하고, `pg_trgm` GIN 을 시험해 결과를 적는다
- [ ] 인덱스의 **비용**도 적는다 — 인덱스 크기, 쓰기 지연
- [ ] `docs/00_overview/02-api.md` · `models.py` 는 고치지 않는다

## 완성 예시

**이 형태를 그대로 따른다.**

`docs/perf-search.md` 는 이런 표를 담는다.

```markdown
## ② 이름 부분 검색 — `WHERE name ILIKE '%김%'`

| | 실행 시간 | 계획 |
|---|---|---|
| 전 | 412 ms | Seq Scan on applications (rows=100000) |
| 후 | 8 ms | Bitmap Index Scan on ix_applications_name_trgm |

**왜 느렸나**: `%김%` 은 앞이 열려 있어 B-tree 가 못 쓴다. 10만 행을 전부 읽고 매칭했다.
**무엇을 걸었나**: `pg_trgm` GIN 인덱스. 3글자 단위로 쪼개 색인하므로 앞이 열린 패턴도 탄다.
**비용**: 인덱스 크기 18MB, INSERT 가 건당 약 0.3ms 느려짐. 지원서 쓰기는 드물어 감당 가능.
```

측정은 이렇게 한다.

```sql
-- 캐시 효과를 줄이려면 여러 번 돌려 중앙값을 쓴다
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM applications
WHERE name ILIKE '%김%' ORDER BY created_at DESC LIMIT 50;
```

```sql
-- 제안 인덱스 (팀장 합의 후 models.py 에 반영)
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX ix_applications_name_trgm ON applications USING gin (name gin_trgm_ops);
CREATE INDEX ix_applications_stage_created ON applications (current_stage, created_at DESC);
```

## 검증 방법

```bash
psql "$DATABASE_URL" -c "select count(*) from applications"
psql "$DATABASE_URL" -c "explain (analyze, buffers) select * from applications where name ilike '%김%' order by created_at desc limit 50"
psql "$DATABASE_URL" -c "select indexrelname, pg_size_pretty(pg_relation_size(indexrelid)) from pg_stat_user_indexes where relname='applications'"
curl -s 'localhost:8000/api/v1/applications?q=김&limit=50' | python -c 'import sys,json;print("API:",json.load(sys.stdin)["took_ms"],"ms")'
```

기대 결과:

- `applications` 가 **10만 건 이상**이다
- `docs/perf-search.md` 에 쿼리 4종의 **전/후 수치**가 표로 있다
- 부분 검색이 인덱스 전 `Seq Scan`, 후 `Index Scan`(또는 Bitmap)으로 **바뀐 것이 계획에 보인다**
- 각 인덱스의 **크기와 쓰기 비용**이 적혀 있다
- API `took_ms` 가 튜닝 전후로 얼마나 줄었는지 PR 본문에 있다
- `models.py` · `docs/00_overview/01-erd.md` 가 변경되지 않았다

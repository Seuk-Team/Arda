# 실시간 면접 시그널링 — 지원자(폰) ⟷ 채용자(PC)

> 이 문서는 작성 시점의 설계·계획이다. 확장·개정은 도메인 오너가 한다([03-conventions](../00_overview/03-conventions.md) "결정 문서 개정").

> **이 문서가 원본이다.** 값을 바꾸면 `backend/app/api/interview_rtc.py` 와 같이 고친다.
> 작성 2026-09-08 · woojeongalex(백엔드·프론트) · 소비자: **앱(minahdev)** · **AI(cloverky)**

## 한 줄

**지원자는 폰으로, 채용자는 PC로 들어와 서로 얼굴을 보고 말한다.** 서버는 둘을 이어 주기만 하고 영상은 지나가지 않는다.

## 비유

전화 교환원입니다. 교환원은 **번호를 이어 줄 뿐 통화 내용을 듣지 않습니다.** 연결되고 나면 두 사람은 교환원을 거치지 않고 직접 이야기합니다.

여기서 "교환원"이 이 문서의 WebSocket 이고, "통화"가 WebRTC 입니다. 그래서 **영상·음성은 우리 서버 대역폭을 쓰지 않습니다.**

---

## 왜 이제 와서 하는가 — 제외였던 것 아닌가

맞습니다. [00-overview](../00_overview/00-overview.md) 가 "실시간 화상면접"을 제외에 두고 있었고, 근거는 [04_planning/00_summary_ko](../04_planning/00_summary_ko.md) §10-④ 였습니다.

> 3인 이상 동시 접속은 시그널링 서버 + TURN + SFU까지 필요하고, 이 항목 하나가 인력 1명의 4주를 소모한다

**그 견적의 전제는 "3인 이상"입니다.** 우리가 하려는 건 **1:1** 이고, 1:1 은 **SFU 가 필요 없습니다** — 참가자가 셋 이상일 때 각자에게 영상을 복제해 뿌리는 중계 서버가 SFU 인데, 둘이면 그냥 서로 직접 붙습니다.

남는 건 시그널링(이 문서, 백엔드 파일 하나)과 TURN(아래 「네트워크」)뿐입니다. 그래서 00-overview 의 제외 문구를 **"3인 이상 다자 화상면접"으로 좁혔습니다.**

## 접속 주소

```
지원자   wss://api.seuk.suvisdev.cloud/api/v1/ws/interview/{token}/rtc
채용자   wss://api.seuk.suvisdev.cloud/api/v1/ws/interview/{token}/rtc?ticket={ticket}
```

`token` 은 **메일 링크의 그 토큰**입니다. 같은 토큰 = 같은 방입니다.

로컬은 `ws://localhost:8000/...` 입니다.

### 채용자는 왜 입장권이 따로 필요한가

**토큰을 아는 사람 아무나 면접관 자리에 앉으면 안 되기 때문입니다.** 링크가 한 번 전달되면 그 사람도 지원자의 얼굴을 보게 됩니다. 그래서 채용자 자리는 로그인을 요구합니다.

그런데 **브라우저의 WebSocket 은 헤더를 붙일 수 없어서** 평소 쓰는 `Authorization: Bearer` 를 못 싣습니다. JWT 를 쿼리스트링에 그대로 넣으면 접속 로그에 장기 토큰이 남습니다. 그래서 **한 번 쓰고 버리는 짧은 입장권**을 REST 로 먼저 받습니다.

```
POST /api/v1/interview-sessions/{session_id}/rtc-ticket     (로그인 필요)

→ 200 {
    "ticket": "…",                 60초 · 1회용
    "token": "…",                  이 토큰으로 방에 들어간다
    "expires_in": 60,
    "ice_servers": [ … ]           아래 「네트워크」 참고
  }
```

**입장권은 접속 직전에 받으세요.** 60초입니다. 재접속할 때마다 새로 받습니다.

지원자는 입장권이 없습니다 — 메일 링크의 토큰이 곧 자격입니다.

## 주고받는 것 — 전부 JSON 텍스트

바이너리는 없습니다. 영상·음성은 이 채널로 다니지 않습니다.

### 서버 → 클라이언트

| `type` | 언제 | 같이 오는 것 |
|---|---|---|
| `hello` | 붙은 직후 (항상 첫 메시지) | `role` · `peer_present` · `should_offer` · `ice_servers` |
| `peer-join` | 상대가 들어옴 | `role` |
| `peer-leave` | 상대가 나감 | `role` |
| `offer` `answer` `ice` | 상대가 보낸 것 그대로 | 원본 필드 + `from` |
| `pong` | `ping` 에 대한 답 | |
| `error` | 문제 | `code` · `message` |

```json
{ "type": "hello", "role": "recruiter", "peer_present": true,
  "should_offer": true, "ice_servers": [{"urls": "stun:stun.l.google.com:19302"}] }
```

### 클라이언트 → 서버

| `type` | 같이 보낼 것 |
|---|---|
| `offer` | `sdp` |
| `answer` | `sdp` |
| `ice` | `candidate` |
| `bye` | |
| `ping` | |

**서버는 `sdp` · `candidate` 안을 들여다보지 않습니다.** 그대로 상대에게 넘기고 `"from"` 만 덧붙입니다. 그래서 WebRTC 스펙이 바뀌어도 서버는 안 고칩니다.

모르는 `type` 은 **조용히 버립니다** — 나중에 메시지가 늘어도 옛 서버가 연결을 끊지 않습니다.

### `error` 의 `code`

| `code` | 뜻 | 클라이언트가 할 일 |
|---|---|---|
| `no_peer` | 상대가 아직 안 들어옴 | 기다렸다 `peer-join` 을 받고 다시 보낸다 |
| `session_closed` | 끝났거나 만료된 면접 | 안내 화면 |
| `replaced` | 같은 자리에 다른 곳에서 접속함 | 이 연결은 닫힌다. 자동 재접속하지 말 것 |
| `too_large` | 쪽지가 128KB 초과 | 보통은 버그다 |

닫기 코드는 `4404`(없는 토큰) · `4401`(입장권 불량) · `4409`(끝난 면접·자리 뺏김)입니다.

## 거는 쪽은 **항상 채용자**입니다

양쪽이 동시에 `offer` 를 내면 협상이 꼬입니다(glare). 그래서 거는 쪽을 하나로 고정했고, **서버가 `hello.should_offer` 로 직접 알려줍니다.** 클라이언트가 각자 판단하지 마세요.

```
지원자 먼저 들어옴        채용자 나중에 들어옴
    │                          │
    ├── hello(should_offer:F)  │
    │                          ├── hello(should_offer:T) → offer 를 만든다
    ├── peer-join ─────────────┤
    │                          │
    │  ←──────── offer ────────┤
    ├──────── answer ─────────→│
    │  ←────── ice ×N ────────→│
    │                          │
    └──── 여기부터 영상·음성은 서버를 안 거친다 ────┘
```

채용자가 먼저 들어와 있으면 `hello.should_offer` 가 `false` 로 오고, 지원자가 들어올 때 `peer-join` 을 받습니다. **`peer-join` 을 받은 채용자도 offer 를 만듭니다.**

정리하면 — **채용자는 `should_offer:true` 이거나 `peer-join` 을 받았을 때 offer 를 만든다. 지원자는 절대 만들지 않는다.**

## 네트워크 — TURN 이 있어야 붙는 경우

WebRTC 는 서로의 공인 주소를 알아야 붙습니다. 그걸 알려주는 게 **STUN** 이고, 그래도 못 붙을 때 **실제로 중계해 주는 것이 TURN** 입니다.

| 상황 | STUN 만으로 | |
|---|---|---|
| 같은 와이파이 | **붙는다** | |
| 집 ↔ 집 (보통 공유기) | 대개 붙는다 | |
| 회사 방화벽 · 일부 LTE | **못 붙는다** | TURN 필요 |

**목록을 클라이언트에 박지 마세요.** 서버가 `hello.ice_servers` 로 줍니다(입장권 응답에도 들어 있습니다). TURN 이 나중에 생겨도 **앱·웹을 다시 배포하지 않아도 되게** 하려는 것입니다.

서버 쪽 설정은 환경변수 하나입니다 — 형식은 WebRTC 표준 그대로입니다.

```
RTC_ICE_SERVERS='[{"urls":"stun:stun.l.google.com:19302"},
                  {"urls":"turn:…:3478","username":"…","credential":"…"}]'
```

기본값은 공용 STUN 하나입니다. **시연 망이 아직 안 정해져서 TURN 은 비워 뒀습니다** — 인프라(suvisdev)에 요청해 둔 상태고, 오면 환경변수만 채웁니다.

## 끊겼을 때

**끊긴 것 자체는 오류가 아닙니다.** 다시 붙으면 됩니다.

- 같은 자리에 새로 붙으면 **옛 연결이 닫힙니다**(`replaced`). 새로고침이 보통 이 경우입니다
- 상대는 `peer-leave` → `peer-join` 을 차례로 받습니다. 받으면 **PeerConnection 을 새로 만드세요** (헌 것을 재활용하면 ICE 상태가 남아 안 붙습니다)
- 재접속 시 채용자는 **입장권을 새로 받아야 합니다** (1회용)

`ping` 은 25초쯤마다 보내는 걸 권합니다. 중간 프록시가 조용한 연결을 끊습니다.

## AI 실시간 분석과의 관계 — 별개 채널입니다

소연님의 실시간 얼굴 분석은 **이 채널을 쓰지 않습니다.** 지금 있는 것을 그대로 씁니다.

```
/ai/ws/interview/{token}      ← ai/lie-detection/PROTOCOL.md (소연님)
/api/v1/ws/interview/{token}/rtc   ← 이 문서 (시그널링)
```

지원자 클라이언트는 **둘 다 열어 둡니다.** 카메라 스트림 하나에서 갈라, 한쪽은 WebRTC 로 채용자에게 보내고 다른 쪽은 JPEG 프레임으로 분석 서버에 보냅니다.

이렇게 나눈 이유는 **원본을 보는 쪽이 정확하기 때문**입니다. 채용자 화면에 도착한 영상은 이미 압축·손실을 거쳤고, 네트워크가 나쁘면 해상도가 떨어집니다. 표정 분석을 그걸로 하면 **네트워크 상태가 판정에 섞입니다.**

> ### 소연님께 — 정해야 할 것 하나
>
> 지금 `interview_ws.py` 는 **AI 가 질문을 하고 말이 끝나면 다음 질문으로 넘기는** 흐름입니다. 사람이 직접 면접을 보는 이 화면에서는 **질문을 아르가 하면 안 됩니다.**
>
> 분석만 하고 질문·전사는 안 하는 모드가 필요할 것 같은데, `?mode=analysis` 같은 걸로 나눌지 아니면 아예 다른 경로로 둘지는 소연님 판단입니다. 정해지면 알려 주세요 — 화면 쪽은 맞추겠습니다.

## 서버 쪽 제약 — 프로세스 하나

방 목록이 **파이썬 딕셔너리**라 이 프로세스 안에서만 유효합니다. uvicorn 워커를 2개 이상으로 올리면 **지원자와 채용자가 서로 다른 프로세스에 붙어 영영 못 만납니다.**

운영은 지금 `--workers` 없이(1개) 돕니다. 늘리려면 방 저장소를 Redis pub/sub 으로 먼저 바꿔야 하고, 그걸 모르고 늘리는 일이 없게 **기동 로그에 한 줄 남깁니다.**

트래픽은 걱정 대상이 아닙니다 — 지나가는 게 쪽지 몇 개라 면접 한 건당 수십 KB 입니다.

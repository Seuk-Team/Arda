# [G4·A4] 설정 화면 실동작 + 메일 발송(수동·에이전트) + 발송 주체 서명

> **PR 단위**: 도메인별로 나눠 각자 main 직접 push. 아래 "작업 순서"의 의존만 지킨다.
> 관련: [ADR-0016](../03_decision/0016-면접-일정-자동화.md)(기존 인프라 재사용 철학) · [ADR-0017](../03_decision/0017-등급-이분화.md)(admin·member 권한 모델) · [01-erd.md](../00_overview/01-erd.md) · [02-api.md](../00_overview/02-api.md) · [email-templates.md](../00_overview/email-templates.md)

## 배경

설정 화면([Settings.tsx](../../frontend/app/src/pages/Settings.tsx))의 4탭 중 실제로 동작하는 것은 `면접 가능 시간` 하나뿐이다. `내 계정`은 저장 API가 없고, `사용자·권한`은 파일 상단 `const USERS` 하드코딩 목데이터 5명이며, `메일 템플릿`은 제목·본문이 `(문구 작성 중)`으로 잠겨 있다.

메일은 **자동 발송만** 있다 — 단계 변경([stages.py](../../backend/app/stages.py) `NOTIFY_STAGES`), 접수(C4), 일정 제안·확정([schedules.py](../../backend/app/api/schedules.py)). 담당자가 임의로 한 통 보낼 경로가 없고, 에이전트의 `draft_email`은 초안 텍스트만 반환하고 발송하지 않는다.

이 지시서는 셋을 한꺼번에 푼다: **설정 4탭 실동작 · 수동/에이전트 발송 · 발송 주체에 따른 서명.**

**새 층을 짓지 않는다.** 메일은 기존 `email_logs` + SQS + 워커(G2)를, 에이전트 발송은 기존 확인 게이트(M4)를, 화면은 기존 4탭을 그대로 쓴다. ADR-0016이 신규 층을 한 층으로 줄여 성공한 방식 그대로다.

## 1. 설계 결정 (확정 — 구현자가 다시 고르지 않는다)

### 결정 1. 메일 템플릿은 코드 기본값 + DB 오버라이드

`mail.py._TEMPLATES`를 **기본값으로 유지**하고, 신규 `email_templates`에 행이 있으면 그것이 우선한다.

전부 DB로 옮기면 시드가 선행돼야 메일이 나간다 — 시드 누락 = 발송 전면 실패다. 오버라이드 방식은 `create_all`이 빈 테이블만 만들면 끝이고, 오버라이드를 지우면 기본 문구로 복귀한다(되돌리기 쉽다).

- `mail.render`는 `db`를 받아 오버라이드→기본값 순으로 읽는다. 호출부는 워커 한 곳뿐이라 파급이 작다.
- **치환을 `str.format` → 순차 `.replace`로 바꾼다.** 사용자가 편집한 본문에 `{`가 섞이면 `format`이 `KeyError`를 던져 워커가 죽고 재시도→DLQ까지 간다. `.replace`는 모르는 토큰을 그대로 둔다.
- 저장 시 허용 변수(`{지원자명}` `{공고명}` `{회사명}` `{면접일시}` `{서명}`) 외의 `{...}` 토큰은 **422**로 거절한다.
- **"문서가 기준" 원칙은 유지하되 범위를 좁힌다.** [email-templates.md](../00_overview/email-templates.md) 머리말과 [mail.py](../../backend/app/mail.py) docstring에 한 줄씩 추가: *"운영 문구는 설정 화면에서 편집하며 `email_templates` 오버라이드가 우선한다. 이 문서와 `_TEMPLATES`는 기본값이다."*
- 프론트 `MAIL_STAGES`의 `서류 검토`는 **대응 템플릿이 없는 유령 탭**이다(`screening`은 발송 없음). 실제 4종으로 교체: **접수 확인(applied) / 면접 안내(interview) / 최종 합격(accepted) / 불합격(rejected)**.

### 결정 2. 수동 발송 본문은 `email_logs`에 싣는다

`email_logs`에 nullable `subject`·`body`를 추가하고, 수동·에이전트 발송은 확정 본문을 행에 실어 `stage='custom'`으로 남긴다. 워커는 `body`가 있으면 렌더를 건너뛰고 그대로 보낸다.

큐·재시도·DLQ·멱등·상태가 한 벌 그대로 재사용되고, 지금 없는 **"무엇을 보냈는가" 감사 기록**이 생긴다.

- `ck_email_logs_stage`에 `custom`을 추가한다. `EMAIL_LOG_STAGES = STAGES + ("custom",)`를 **별도 상수로** 둔다 — `applications.current_stage` 등 다른 stage 제약은 건드리지 않는다.
- `application_id` NOT NULL은 **유지한다.** 제약이 아니라 안전장치다: 수신 주소를 서버가 `application.email`에서만 읽게 해서 **임의 주소 발송 경로를 아예 만들지 않는다.** 에이전트 오발송의 반경이 여기서 정해진다.
- `stage='custom'`인데 `body`가 없는 행은 `UnknownStageTemplate`과 같은 경로로 `failed` 처리한다.
- **자동 발송 경로는 한 줄도 바꾸지 않는다.** `subject`·`body`가 NULL이면 지금처럼 발송 시점 렌더다 — 라이브 일정 링크를 싣는 `worker._interview_at`이 발송 시점 렌더를 전제한다.

### 결정 3. 에이전트는 `send_email` 신규 도구 (draft_email 확장이 아니다)

초안은 부수효과가 없으니 확인 게이트 밖, 발송은 되돌릴 수 없으니 게이트 안이다. 한 도구에 섞으면 승인 한 번의 의미가 이중이 된다.

안전장치 5겹:

1. **수신자를 파라미터로 받지 않는다** — `application_id`로 DB의 주소만 쓴다
2. **확인 게이트 필수** — `WRITE_TOOL_NAMES`에 추가해 기존 `pending_action` → `POST /agent/confirm` 경로를 탄다. 새 게이트를 만들지 않는다
3. **확인 카드에 전문 표시** — 현재 카드는 `description` 한 줄뿐이다. `send_email`에 한해 수신자·제목·본문 전문을 렌더한다
4. **감사 기록** — 승인된 본문이 결정 2 덕에 `email_logs`에 그대로 남는다
5. **수동 발송 API와 같은 서비스 함수**를 쓴다 — 순서를 따로 써서 메일이 증발했던 사고(#148)의 교훈

`draft_email`의 하드코딩 templates dict는 **삭제**하고 `mail.get_template`을 재사용한다(purpose→stage 매핑). 지금 `mail.py`와 문구가 다른 이원화가 구조적으로 사라진다. `draft_email`은 게이트에서 뺀다.

### 결정 4. 사용자 관리는 목록·역할 변경·비활성화. 삭제는 만들지 않는다

`users.id`는 `created_by`·`evaluator_id`·`assigned_by`·`changed_by`로 도처에 박혀 있다 — 삭제는 이력을 부순다. 화면의 `상태` 컬럼이 이미 비활성화 모델을 전제하고 있다.

- `users.is_active` 추가. 차단 지점 둘: `auth.login`(401)과 `deps.get_current_user` — **이미 발급된 토큰도 즉시 무력화**된다.
- **잠금 방지 규칙 하나: 활성 admin 수를 0으로 만드는 변경은 409.** 강등이든 비활성화든, 자기 자신이든 남이든 같은 규칙이다. '자기 자신 금지'로 쪼개지 않는다 — admin이 둘이면 자기 강등도 정당한 조작이다.
- 사용자 추가는 **기존 `POST /auth/signup`**(admin 전용)을 쓴다. 신규 API 없음, 프론트 모달만.

### 결정 5. "admin·member 둘 다 설정 가능"의 해석

member에게 admin 탭을 여는 것이 아니다. **member도 설정 화면에서 실제로 저장되는 것이 있어야 한다**는 뜻이다. 역할별로 새 화면을 분기하지 않고 기존 4탭 안에서 푼다.

| 탭 | 노출 | 작업 후 동작 | 근거 |
|---|---|---|---|
| 내 계정 | 전원 | 이름·비밀번호 저장 (`PATCH /auth/me` 신규) | member의 "설정 가능"이 여기서 실현된다 |
| 사용자·권한 | admin | 실목록 + 역할 변경 + 활성/비활성 + 추가 모달 | 계정 생성 admin 전용 (ADR-0017) |
| 메일 템플릿 | admin | 4종 편집·저장·기본값 복귀 | 메일 템플릿 admin 전용 (ADR-0017) |
| 면접 가능 시간 | 전원 | 변경 없음 | ADR-0016 |

**수동 발송 UI는 설정이 아니라 지원자 상세 패널**([ApplicantPanel.tsx](../../frontend/app/src/pages/ApplicantPanel.tsx))에 붙인다. 발송 권한은 로그인 전원 — member의 단계 변경이 이미 메일을 발송하므로 수동 발송만 admin으로 좁힐 논리가 없다.

### 결정 6. 서명은 발송 주체에 따라 달라진다

지금은 4종 전부가 `{회사명} 채용 담당자 드림`으로 끝난다. 주체가 사람인지 아르인지 구분이 없다.

**주체 3종**

| `actor_kind` | 언제 | 서명 |
|---|---|---|
| `human` | 사람이 UI에서 트리거·작성 (단계 변경, 수동 발송, 일정 제안 생성) | `{회사명} 채용 담당자 {담당자명} 드림` |
| `agent` | 아르가 문안을 작성 (`send_email` 도구) | `{회사명} 채용 에이전트 아르 드림` |
| `system` | **지원자 본인의 행동이 트리거** (접수 확인, 일정 확정 통보) | `{회사명} 채용팀 드림` |

`system`이 필요한 이유: 접수 확인은 지원자가 제출해서, 확정 통보는 지원자가 슬롯을 눌러서 나간다. 둘 다 사람 담당자도 아르도 주체가 아니다. 여기에 담당자 이름을 넣으면 거짓이다.

**예외 규칙 — 결정 통보는 무조건 사람 이름.** `accepted`·`rejected` 템플릿 발송은 `actor_kind`와 무관하게 `human` 서명을 쓴다(`actor_id`의 이름). 에이전트 발송도 확인 게이트가 있어 **최종 승인은 항상 사람**인데, 서명만 보면 AI가 결정한 것처럼 읽힌다. 채용에서 "심사도 AI가 했나"라는 오해는 비싸다. 발표용 "에이전트가 메일을 보낸다"는 면접 안내 쪽으로 충분히 보여진다.
*(잔여 간극: 아르가 `send_email`로 불합격 취지의 `custom` 메일을 쓰면 이 규칙에 안 걸린다. 확인 카드 전문 표시로 사람이 걸러내는 것에 맡긴다.)*

**구현**

- 템플릿 본문 끝의 서명 줄을 `{서명}` **변수로 뺀다.** 안 그러면 admin이 템플릿을 편집하다 서명을 지운다. 허용 변수에 포함하고, 저장 시 `{서명}`이 없으면 본문 끝에 자동으로 붙인다.
- 담당자 이름은 `users.name`을 쓴다. 표시명 컬럼을 새로 만들지 않는다.

### 결정 7. `ReplyTo`를 채운다 — 서명보다 먼저 고칠 것

**현재 4종 템플릿 전부가 "이 메일에 회신해 주시기 바랍니다"라고 하는데, 발신은 `no-reply@arda.seuk.cloud`이고 [worker.py](../../backend/app/worker.py) `_send_via_ses`에 `ReplyTo`가 없다. 지원자 회신이 전부 증발한다.** 여기에 담당자 실명까지 붙으면 이름은 있는데 답장은 안 가는 상태가 된다.

- `_send_via_ses`에 `ReplyToAddresses`를 넘긴다. `actor_kind='human'`이면 그 사람의 `users.email`, `agent`·`system`이면 팀 공용 주소.
- 팀 공용 주소는 환경변수 `MAIL_REPLY_TO`. 미설정이면 기동 시 경고 로그를 남긴다(발송은 막지 않는다).


### 결정 8. From 표시 이름은 주체를 따르고, 발신 주소는 하나로 둔다 (2026-09-01 추가)

받은편지함에 `Arda 채용 담당자 김채용 <no-reply@arda.seuk.cloud>` 로 뜬다. 표시 이름은 본문 서명과 **같은 문자열**(`mail.sender_name`)을 쓴다 — 둘을 따로 만들면 목록에는 A 로 뜨는데 본문 끝은 B 로 끝나는 메일이 생긴다.

**발신 주소를 담당자별로 나누지 않는다.** 팀원 주소가 외부 메일(gmail)이라 그것을 From 에 넣으면 DMARC 정렬이 깨져 스팸함으로 가고, 회사 도메인으로 바꾸려면 받을 메일함(Workspace 계약)이 선행 조건이다 — 코드가 아니라 인프라 결정이다. 표시 이름 + Reply-To 조합이면 **개인 발신 계정 없이도 "누구에게 연락하면 되는가"가 성립한다.**

나중에 진짜 per-user 발송으로 갈 때도 스키마·API 는 안 바뀐다. `email_logs.actor_id` 가 이미 주체를 남기고 있어서, 바뀌는 것은 워커가 `Source` 를 만드는 한 줄뿐이다.

한글 이름은 헤더에 날것으로 못 넣는다 — `email.utils.formataddr` 가 MIME 인코딩한다.

## 2. 스키마 변경 (01-erd.md v1.5 — 코드와 같은 커밋에서 갱신)

**users — 컬럼 추가**

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| is_active | boolean | NOT NULL, default true | 비활성 계정은 로그인·토큰 사용 불가. 삭제 대체(FK 이력 보존) |

**email_logs — 컬럼 추가 + 제약 변경**

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| subject | text | NULL 허용 | 수동·에이전트 발송의 확정 제목. NULL = 자동 발송(발송 시점 렌더) |
| body | text | NULL 허용 | 확정 본문. 보낸 그대로 남는 감사 기록 |
| actor_kind | varchar(10) | NOT NULL, default `'system'`, CHECK(`human`/`agent`/`system`) | 발송 주체 — 서명·ReplyTo가 이 값으로 갈린다 |
| actor_id | bigint | FK → users.id, NULL 허용 | `human`·`agent` 일 때의 사람(에이전트는 승인자). `system`이면 NULL |
| stage | (기존) | CHECK 에 `custom` 추가 | `custom` = 수동·에이전트 발송. 이때 subject·body 필수(코드 검증) |

**email_templates — 신규 테이블**

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | bigint | PK | |
| stage | varchar(20) | UNIQUE, NOT NULL, CHECK(`applied`/`interview`/`accepted`/`rejected`) | 행이 없으면 코드 기본값 사용 |
| subject | varchar(255) | NOT NULL | 허용 변수 외 `{...}` 토큰은 422 |
| body | text | NOT NULL | 위와 동일. `{서명}` 없으면 자동 append |
| updated_by | bigint | FK → users.id, NOT NULL | 마지막 수정자 |
| created_at / updated_at | timestamptz | NOT NULL | |

**이행**

`email_templates`는 `create_all`이 만든다(신규 테이블). **`users`·`email_logs` 변경은 `create_all`이 못 한다** — 1회성 SQL `backend/scripts/upgrade_settings_mail.sql`을 만들고 [07-deploy.md](../00_overview/07-deploy.md) "1회성 DB 이행" 표에 행을 추가한다.

- `migrate_roles_to_member.sql`과 같은 관례: 트랜잭션 하나, `ON_ERROR_STOP=1`, 모르는 값이 있으면 일부러 멈춘다.
- `ADD COLUMN IF NOT EXISTS`로 멱등하게 쓴다(재실행 무해).
- **실행 순서가 역할 이행과 반대다: SQL 먼저 → 재배포 나중.** 새 코드의 ORM이 `is_active`를 SELECT에 실으므로 컬럼 없이 새 코드가 뜨면 전 요청이 죽는다. 구 코드는 새 컬럼이 있어도 무해하다.

## 3. API 변경 (02-api.md — 코드와 같은 커밋에서 갱신)

**인증 (A) — 추가**

| 메서드 | 경로 | 권한 | 비고 |
|---|---|---|---|
| PATCH | `/api/v1/auth/me` | 로그인 전원 | 본문 `{name?, current_password?, new_password?}`. 비밀번호 변경은 `current_password` 필수 — 불일치 **401**. email·role은 못 바꾼다 |

**사용자 (A4) — 신규 절**

| 메서드 | 경로 | 권한 | 비고 |
|---|---|---|---|
| GET | `/api/v1/users` | 로그인 전원 (조회 개방, ADR-0017) | `{id, name, email, role, is_active, created_at}` |
| PATCH | `/api/v1/users/{id}` | **admin** | 본문 `{role?, is_active?}`. 활성 admin 이 0 이 되는 변경은 **409** |

로그인·토큰 검증에 비활성 차단 추가: **401** "비활성화된 계정입니다".

**메일 (G4) — 신규 절**

| 메서드 | 경로 | 권한 | 비고 |
|---|---|---|---|
| GET | `/api/v1/email-templates` | 로그인 전원 | 4종. 항목마다 `source: "default" \| "custom"` |
| PUT | `/api/v1/email-templates/{stage}` | **admin** | 본문 `{subject, body}`. 허용 외 변수 **422**, 4종 외 stage **404** |
| DELETE | `/api/v1/email-templates/{stage}` | **admin** | 오버라이드 삭제 = 기본값 복귀. 없으면 **404** |
| POST | `/api/v1/applications/{id}/emails` | 로그인 전원 | 수동 발송. 본문 `{subject, body}` — 수신자는 서버가 지원자 email 로 고정. `email_logs(stage=custom, actor_kind=human, actor_id=본인)` 생성 + **커밋 후** SQS 발행 |
| GET | `/api/v1/applications/{id}/emails` | 로그인 전원 | 발송 이력(자동·수동 통합, 최신순) |

에이전트는 REST 변경 없음 — `/agent/chat`·`/agent/confirm` 재사용. 도구 추가는 [TOOLS.md](../../backend/app/agent/TOOLS.md)에 기록.

## 6. 리스크

- **잘못 보낸 메일은 되돌릴 수 없다.** 통제: 수신자를 사람·에이전트가 입력 불가(DB 고정) · 에이전트는 전문 확인 후 승인 필수 · 수동 발송도 확인 모달 · 보낸 본문이 DB에 남음 · 변수 검증으로 깨진 문구 차단. 잔여 위험은 "사람이 전문을 읽고도 승인"뿐이다.
- **이행 순서 사고.** SQL 전에 새 코드가 뜨면 전 요청 500. `07-deploy.md`에 **"SQL 먼저 → 재배포"**로 못박고 SQL을 멱등으로 쓴다.
- **프론트(Vercel 자동)·백엔드(수동 배포) 어긋남.** F 커밋을 먼저 올리면 운영 프론트가 없는 API를 때린다. **백엔드 push → 팀 채널 재배포 요청 → 배포 Swagger 확인 → 그 다음 프론트 push.**
- **체크 제약 교체 실패.** 모르는 stage 값이 있으면 멈춘다 — 트랜잭션 하나라 반쪽 상태는 없다.
- **잠금 사고.** 마지막 활성 admin 가드가 유일한 방벽이다. 만일 잠기면 `scripts/create_admin.py`가 탈출구다.
- **도메인 경계.** 이 지시서는 백엔드·에이전트·프론트를 가로지른다. 남의 폴더를 고쳤으면 커밋 메시지에 명시하고 팀 채널에 사후 한 줄 ([03-conventions.md](../00_overview/03-conventions.md)).

# [H4·H5] 정렬 + 커서 페이지네이션

> 담당: 팀원2 · 역할 B(검색·데이터) · 브랜치: `feat/h4-sort-pagination`
> **PR 단위**: 이 지시서 전체 = PR 1개

## 배경

`OFFSET` 은 건너뛸 행을 **전부 읽고 버린다.** 10만 건에서 `OFFSET 90000` 이면 9만 행을 읽고 50건을 준다. 뒤로 갈수록 느려지고, 그 사이 새 지원서가 들어오면 행이 밀려 **같은 지원자가 두 페이지에 나온다.**

커서 방식은 "마지막으로 본 행 다음부터"를 조건으로 걸어 항상 같은 비용으로 읽는다.

**이것이 이 사람의 면접 카드 재료다** — "왜 offset 을 안 썼는가".

## 선행 조건 — 없으면 중단

아래가 하나라도 아니면 **시작하지 말고 팀 채널에 알린다.** 없는 것을 상상해서 만들지 않는다.

- [ ] [H2 검색 · 필터 API](H2-검색-필터-API.md) PR이 머지돼 있다
- [ ] [J7 파트B](J7-더미데이터-생성기.md)로 더미가 최소 1만 건 이상 들어 있다 — 적으면 차이가 안 보인다

## 가장 중요한 규칙

- **[backend/app/models.py](../../backend/app/models.py)를 수정하지 않는다.** 컬럼이 부족해 보여도 추가하지 않는다. 멈추고 팀 채널에 묻는다.
- **[docs/00_overview/01-erd.md](../00_overview/01-erd.md)·[docs/00_overview/02-api.md](../00_overview/02-api.md)를 수정하지 않는다.** 공용 문서다.
- **인증·권한 코드를 넣지 않는다.** 인증은 팀장 담당(A1~A3)이고 아직 없다. 토큰 검사를 흉내 내면 나중에 팀장 것과 충돌한다. 사용자 id 가 필요한 자리는 `# TODO(A1): 토큰의 사용자로 채운다` 주석만 남긴다.
- **`main.py` 는 `include_router` 한 줄만** 건드린다. 그 파일의 다른 부분은 손대지 않는다.
- **`backend/app/api/search.py` 만 고친다.**
- **`offset` 파라미터를 지우지 않는다.** 화면이 아직 쓰고 있을 수 있다. 커서를 추가하고 offset 은 남겨둔 채 문서에 "커서를 권장"이라고 적는다.
- **정렬 키에는 반드시 `id` 를 tie-breaker 로 붙인다.** 같은 시각의 행이 여러 개면 순서가 흔들려 커서가 깨진다.

## 완료 조건

- [ ] 정렬 `sort` — `created_at` (기본) · `score` (평가 평균). `order` — `desc`(기본) · `asc`
- [ ] 허용 밖 `sort`·`order` → **422**
- [ ] **모든 정렬에 `id` tie-breaker** 를 함께 건다 (`ORDER BY created_at DESC, id DESC`)
- [ ] 커서 `cursor` — 마지막 행의 정렬 키를 base64 로 인코딩한 불투명 문자열
- [ ] 응답에 `next_cursor` 포함. 다음 페이지가 없으면 `null`
- [ ] `score` 정렬은 `evaluations` 평균과 LEFT JOIN. **평가가 없는 지원자가 사라지면 안 된다**
- [ ] 커서와 `offset` 을 동시에 주면 **커서가 이긴다**
- [ ] `docs/00_overview/02-api.md` 는 고치지 않는다 — 팀장에게 갱신을 요청하고 PR 본문에 적는다

## 완성 예시

**이 형태를 그대로 따른다.**

```python
# backend/app/api/search.py (추가분)
import base64, json

SORTS = {"created_at": Application.created_at, "score": None}  # score 는 집계라 따로 처리


def _encode(row) -> str:
    # 커서는 불투명 문자열이다. 클라이언트가 내용을 알 필요도, 만들 필요도 없다
    return base64.urlsafe_b64encode(
        json.dumps({"v": row.created_at.isoformat(), "id": row.id}).encode()
    ).decode()


def _apply_cursor(stmt, cursor: str, desc: bool):
    c = json.loads(base64.urlsafe_b64decode(cursor))
    # (정렬키, id) 튜플 비교 — id 가 없으면 같은 시각의 행에서 순서가 흔들려 커서가 깨진다
    if desc:
        return stmt.where(tuple_(Application.created_at, Application.id)
                          < (c["v"], c["id"]))
    return stmt.where(tuple_(Application.created_at, Application.id) > (c["v"], c["id"]))
```

`score` 정렬은 LEFT JOIN 이어야 한다. INNER JOIN 을 쓰면 **평가가 없는 지원자가 목록에서 사라진다.**

```python
avg_score = func.avg(Evaluation.score).label("avg_score")
stmt = (select(Application, avg_score)
        .outerjoin(Evaluation, Evaluation.application_id == Application.id)
        .group_by(Application.id)
        .order_by(avg_score.desc().nullslast(), Application.id.desc()))
```

## 검증 방법

```bash
A=localhost:8000/api/v1/applications
curl -s "$A?sort=score&order=desc&limit=5" | python -c 'import sys,json;d=json.load(sys.stdin);print("score정렬",[i.get("avg_score") for i in d["items"]])'
C=$(curl -s "$A?limit=50" | python -c 'import sys,json;print(json.load(sys.stdin)["next_cursor"])')
curl -s "$A?limit=50&cursor=$C" | python -c 'import sys,json;d=json.load(sys.stdin);print("2페이지",len(d["items"]),d["took_ms"],"ms")'
echo '--- 깊은 페이지 비교'
curl -s "$A?limit=50&offset=90000" | python -c 'import sys,json;print("offset 90000:",json.load(sys.stdin)["took_ms"],"ms")'
curl -s -o /dev/null -w '이상한정렬 %{http_code}\n' "$A?sort=없는키"
```

기대 결과:

- `sort=score` 로 평균 점수 내림차순이 된다
- **평가가 없는 지원자도 목록에 남아 있다** (avg_score 가 null)
- `next_cursor` 로 다음 페이지가 이어지고 **중복 행이 없다**
- 깊은 페이지에서 **커서가 offset 보다 확연히 빠르다** — 두 수치를 PR 에 적는다
- `sort=없는키` → **422**
- 마지막 페이지의 `next_cursor` 가 `null`

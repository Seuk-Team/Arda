# RAG 범위 정리 — 소주제 4번 담당 검토

> 작성: 2026-09-01 · woojeongalex (발표 소주제 4번 담당)
> 대상 결정: [06-weekly](00_overview/06-weekly.md) E #12 · #13
> 관련: [ADR-0021](03_decision/0021-RAG-시맨틱-검색.md) · [presentation-outline](presentation-outline.md) §4 · [00_summary_ko](04_planning/00_summary_ko.md) §11

## 결론 먼저

**약속과 어긋난 것이 없다.** 06-weekly #12 와 인수인계 #3 이 공유하는 전제 — *"소개문 4번이 약속한
RAG 는 면접 전사 → 근거 인용 요약인데 들어간 것은 자소서 시맨틱 검색이라 대상이 다르다"* — 는
원문 대조에서 성립하지 않는다. **"약속을 좁혀 다시 쓰거나 새로 구현하거나" 둘 다 필요 없다.**

진짜 문제는 다른 것이고, 아래 §3 에 있다.

## 1. 3단 대조

| 문서 | RAG 를 뭐라고 적었나 | 상태 표기 |
|---|---|---|
| **소개문** [00_summary_ko](04_planning/00_summary_ko.md) §11 ③ | "**서류 기반 RAG 질의응답.** 지원자 정보에 대한 자연어 질의. 단독으로는 변별력이 약하므로 ①②의 보조로 배치한다" | 보조 |
| **발표 뼈대** [presentation-outline](presentation-outline.md) §4 2문단 | "STT→RAG→sLLM 면접 분석 파이프라인(면접 전사 → … → 근거 인용 요약)" | **📋 계획** 이라고 명시 |
| **실제 구현** [ADR-0021](03_decision/0021-RAG-시맨틱-검색.md) · #151 | 지원자 서류(스킬·학력·경력) 임베딩 + 키워드 하이브리드 검색 | ✅ 출하 |

읽어야 할 것은 두 가지다.

1. **소개문이 약속한 RAG 는 "서류 기반"이다.** 면접 전사가 아니다. 구현된 것은 이 약속에 들어맞는다.
2. **면접 전사 RAG 는 발표 뼈대에서 이미 "계획"으로 표기돼 있다.** 완료라고 주장한 문장이 없다.
   [presentation-outline](presentation-outline.md) §4 는 1문단 끝에 "— 여기까지 완료." 를 찍고
   2문단을 "…는 **계획**이다" 로 닫는다. 시제가 뒤집힌 곳이 없다.

즉 **거짓 주장이 없으므로 고쳐 쓸 문장도 없다.** 08/31 발표 뼈대를 쓸 때 이미 정확하게 잘라 뒀다.

## 2. 어디서 오해가 생겼나

소주제 4번 제목이 `LLM 도구 호출 에이전트 + AI 원가 관측 ✅ / STT 면접 분석 📋` 인데,
**본문에서 "RAG" 라는 단어가 📋 쪽에만 등장한다.** 그래서 §4 만 읽으면

- 이 프로젝트의 RAG = 면접 전사 RAG = 계획

으로 읽힌다. 그런데 실제로 출하된 RAG 가 따로 있으니 "약속과 다른 게 들어갔다" 로 보인다.
**틀린 것은 구현이 아니라, 출하된 것이 발표 문서 어디에도 안 적혀 있다는 사실이다.**

## 3. 진짜 문제 — 출하했는데 발표에 없다

`search_applications` 의 시맨틱 검색은 **어느 소주제에도 걸려 있지 않다.**

- 소주제 1 은 검색을 다루지만 **성능 튜닝**(111ms → 7.8ms)만 적혀 있다 — 의미 검색은 없다
- 소주제 4 의 RAG 문단은 계획 쪽이다
- 시연 시나리오 6단계에도 "10만 건에서 즉답 — 성능 수치" 뿐이다

**"Python 경험자 찾아줘" 가 정답 7명을 내는 것**([8a48191](https://github.com/Team-Seuk/Arda/commit/8a48191) 실측)은
도구 호출 에이전트의 가장 보여주기 좋은 장면인데 발표 어디에도 자리가 없다.

부가로, 이 상태로 발표하면 **"RAG 했습니다"라고 말하는 순간 청중은 계획 쪽(면접 전사)으로 알아듣는다.**
같은 단어가 출하물과 계획을 동시에 가리키고 있다.

## 4. 팀장이 고를 것

| | 무엇 | 드는 것 | 잃는 것 |
|---|---|---|---|
| **1안 (권장)** | 소주제 4 문장은 **그대로 둔다**(이미 정확). 시맨틱 검색을 **소주제 1 에 완료 항목으로 편입**하고, 발표에서 출하물은 "시맨틱 검색", "RAG" 는 계획 쪽에만 쓴다 | 문서 2~3줄. 코드 0 | 없음 |
| 2안 | 소주제 4 를 `도구 호출 + 원가 관측 + 서류 시맨틱 검색 ✅ / STT 면접 분석 📋` 로 넓힌다. 소개문 ③ 이 "①②의 보조"로 배치해 둔 근거가 있다 | 문서 갱신 | 4번이 주제 3개가 된다. 발표 §4 기술 깊이 2.5분에 안 들어간다 |
| 3안 | 면접 전사 RAG 를 실제로 구현한다 | STT + 전사 + 근거 검색 + 평가 연동 | **09/04 불가.** 09/30 도 STT·`evaluations` 설계까지 물려 위험 |

**1안을 권한다.** 유일하게 D-3 에 안전하고, 출하물을 되찾아오면서, 계획을 계획으로 유지한다.
용어만 분리하면 "RAG 를 약속했는데 검색만 했다" 는 질문 자체가 성립하지 않는다.

## 5. 별건 — 06-weekly #13 (ADR-0021 개정 여부)

임베딩 입력에서 자기소개서를 뺀 건([ADR-0021](03_decision/0021-RAG-시맨틱-검색.md) 구현 메모)은
**ADR 을 개정하는 쪽이 맞다.** 근거가 실측이고(모델 `max_seq_length` 128 토큰 · 자소서 포함 시
적합자가 15명 중 10위) `EMBEDDING_INCLUDE_INTRO=1` 로 되돌릴 길도 남아 있다. 결정과 실제가
다른 채로 두면 다음 사람이 ADR 을 믿고 되돌린다.

다만 **이건 에이전트 오너(suvisdev) 도메인이다.** 여기서는 의견까지만 남긴다.

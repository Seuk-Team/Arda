# ADR-0011. 에이전트 모델·비용

- 상태: **확정** (2026-08-25) — 제안대로 채택 (단가 대조 완료, 토큰량은 W3 실측 갱신)
- 작성: suvisdev (에이전트)
- 선행: [ADR-0003](0003-ai-추천만.md) · [ADR-0008](0008-에이전트-앱-정식-트랙-승격.md) · [role/agent.md](../01_role/agent.md) §3
- 번호: 0010은 앱 스택([ADR-0008](0008-에이전트-앱-정식-트랙-승격.md) 후속 목록)으로 예약돼 있어 0011을 쓴다

## 맥락

에이전트 트랙에 LLM 호출이 두 군데 생긴다.

| 용도 | 언제 | 특성 |
|---|---|---|
| **이력서 요약·구조화** | 지원서 접수 시 1회 (W3 M2) | 건수가 지원자 수만큼 늘어난다 — **비용이 데이터 양에 비례** |
| **도구 호출 에이전트** | 담당자가 문장을 입력할 때 (W4~W5) | 호출 수는 적지만 **정확도가 데모 품질을 결정** |

두 용도의 요구가 다르므로 모델을 하나로 고정하면 한쪽이 손해다. 그리고 요약 쪽은 [J7 더미 10만 건](../02_tasks/J7-더미데이터-생성기.md)과 맞물려 **사고 시 금액이 큰 쪽**이다.

## 검증한 것 / 검증하지 못한 것

- **검증함**: 추출 파이프라인은 LLM 없이 동작한다. [추출 PoC](../../backend/app/agent/extract/POC-RESULT.md) 20건은 호출 0건으로 텍스트를 얻었다 — LLM은 "추출"이 아니라 **"요약·구조화"에만** 필요하다. 비용이 붙는 지점이 좁혀졌다.
- **검증 못함**: 단가와 실제 토큰 사용량. 아래 표는 [role/agent.md](../01_role/agent.md) §3의 제안값을 그대로 옮긴 것이고, **확정 전에 벤더 가격 페이지와 실호출 1건의 usage 로그로 대조해야 한다.** 대조 결과가 다르면 이 문서의 숫자를 고치고 확정한다.

## 결정 (제안)

### 1. 용도별로 모델을 나눈다

| 용도 | 모델 | 이유 |
|---|---|---|
| 도구 호출 에이전트 | `claude-opus-5` | 문장 → 도구 순차 호출의 정확도가 곧 데모다. 여기서 아끼면 발표가 깨진다 |
| 이력서 요약·구조화 | `claude-haiku-4-5` | 정해진 형식으로 요약하는 작업. 건수가 많아 단가가 지배적 |
| 개발 중 반복 실행 | `claude-haiku-4-5` | 프롬프트를 다듬는 동안 opus를 돌리지 않는다 |

요약을 haiku로 시작하되, **검수 단계에서 품질이 부족하면 요약만 opus로 승격**한다(코드 상수 한 줄). 반대 방향(도구 호출을 haiku로 내리는 것)은 하지 않는다.

### 2. 비용 감 (제안값 기준 — 확정 전 재확인 대상)

요약 1건 ≈ 입력 3K + 출력 0.5K 토큰 가정.

| 모델 | 1건 | 데모 500건 | 더미 10만 건 |
|---|---|---|---|
| `claude-opus-5` (입력 $5 / 출력 $25 per 1M) | ≈ $0.028 | ≈ $14 | ≈ **$2,750** |
| `claude-haiku-4-5` (입력 $1 / 출력 $5 per 1M) | ≈ $0.006 | ≈ $3 | ≈ **$550** |

**오른쪽 열이 이 ADR의 존재 이유다.** 10만 건에 요약을 돌리는 순간 어느 모델이든 사고다 — 그래서 가드가 모델 선택보다 중요하다.

### 3. 비용 가드 (가드가 결정의 본체다)

1. **더미 데이터에 LLM을 호출하지 않는다.** [J7](../02_tasks/J7-더미데이터-생성기.md) 생성기는 `ai_summary`를 NULL로 두거나 문장 은행에서 채운다. 요약 생성 경로는 **접수 훅과 명시적 재생성 버튼** 두 곳뿐이고, 배치·스크립트에서 호출하지 않는다.
2. **호출마다 토큰 사용량을 로깅한다.** 모델명·입력/출력 토큰·소요 시간을 구조화 로그로 남긴다([J5](../02_tasks/J5-로깅-에러표준화.md) 형식에 맞춘다). 발표에서 "얼마 썼나"에 숫자로 답한다.
3. **API 키는 `.env`에만.** 코드·로그·PR 본문에 남기지 않는다 ([CLAUDE.md](../../CLAUDE.md) 금지 절).
4. **재생성은 사람이 누를 때만.** 접수 시 1회 생성·저장하고 상세 패널은 저장값을 표시한다 — 패널을 열 때마다 호출하면 연속 심사에서 비용이 선형으로 늘어난다 ([01-erd.md](../00_overview/01-erd.md) `applications` 비고).

### 4. 기록·재현성

- 생성에 쓴 모델명을 `applications.ai_summary_model`(varchar 50)에 저장한다 — ERD에 컬럼이 이미 있다. 모델을 바꿔도 **어느 요약이 어느 모델 산출인지** 남는다.
- 프롬프트는 `backend/app/agent/prompts/` 아래 파일로 버전 관리한다. 코드에 문자열로 흩어놓지 않는다.

### 5. 키가 없거나 API가 죽었을 때

**요약 실패가 지원 접수를 막지 않는다.** `ai_summary`를 NULL로 두고 화면에는 "요약 없음"으로만 보인다 — 추출 실패([PoC 결과표](../../backend/app/agent/extract/POC-RESULT.md) 폴백 규칙)와 같은 처리다. 접수 트랜잭션 안에서 LLM을 기다리지 않는다.

## 감수하는 것

- **요약 품질이 haiku에서 부족할 수 있다.** 승격 경로(위 1번)를 열어두고, W3 검수 단계에서 샘플로 판정한다.
- **단가는 바뀔 수 있다.** 그래서 이 문서는 단가 자체가 아니라 **가드와 기록 방식**을 결정으로 삼는다. 숫자가 틀려도 가드는 유효하다.

## 2026-08-31 — 일일 예산 소진: 원인과 조치

**증상**: 08/31 API 토큰 예산이 하루 만에 소진됐다. 모델은 haiku(입력 $1 / 출력 $5)였다.

### 추적이 안 됐다 — 가드가 출력 단계에서 무효화돼 있었다

§3-2("호출마다 토큰 사용량을 로깅한다")는 **코드상 지켜지고 있었다.** `runtime.py` 도
`summarizer.py` 도 `extra={"input_tokens":…, "cost_usd":…}` 로 넘기고 있었다. 그런데
`logging_conf.py` 의 `JSONFormatter` 가 `request_id`·`method`·`path`·`status`·`duration_ms`
**다섯 개만 화이트리스트로 골라 담아서**, 토큰·비용 필드가 전부 버려졌다. 남는 로그는

```json
{"ts": "...", "level": "INFO", "message": "agent_run"}
```

호출이 있었다는 사실만 남고 숫자가 없다. `user_id` 도 남기지 않아 "누가 썼나"에도 답할
수 없었다. 게다가 로그는 stdout(`docker logs`)뿐이라 **같은 날 재배포·재시작 루프**
([07-deploy.md](../00_overview/07-deploy.md))로 이미 유실된 뒤였다.

> **교훈**: 로깅은 넣은 것만으로 지켜지지 않는다. 출력까지 눈으로 확인해야 가드다.

### 구조적 원인 (채팅 경로)

요약은 1건 $0.006 수준이고 운영 지원자가 7명이라 지배적이지 않다. 비용은 채팅에 있다.

| # | 원인 | 조치 |
|---|---|---|
| 1 | 고정부(시스템 프롬프트 9.2KB + 도구 정의 11개 10.7KB ≈ 5~7K 토큰)를 **매 호출 정가로 재과금** | 프롬프트 캐싱(`cache_control`) |
| 2 | 담당자 이름이 프롬프트 6번째 줄 → **사람마다 캐시가 갈림** | `agent.v1.md` v5 — 담당자 절을 맨 뒤로 (앞 99.3%가 전원 공통) |
| 3 | 도구 루프가 라운드마다 `messages` 전체를 재전송 (`MAX_ROUNDS=10`) | 1·4로 완화. 왕복 자체는 도구 호출의 원리라 줄일 수 없다 |
| 4 | 대화 이력 상한 없음 — 프론트가 전 이력을 보내고 서버도 자르지 않았다 | `MAX_HISTORY_MESSAGES=20` |
| 5 | `search_applications` 기본 50건·최대 200건이 도구 결과로 들어와 **이후 모든 라운드에 재전송** | 기본 10 · 최대 50 |

### 캐싱에서 반드시 확인할 것

- **haiku-4-5 의 최소 캐시 가능 프리픽스는 4,096 토큰**이다. 모델마다 다르고 세대순도
  아니다(opus-5 512 · sonnet-5 1,024 · haiku-4-5 4,096). 우리 고정부가 그 위이긴 하나
  여유가 크지 않고, **미달하면 에러 없이 조용히 캐시가 안 걸린다.**
  → `cache_read_tokens` 로 확인한다. 반복 호출에서 계속 0이면 안 걸린 것이다.
- **비용 집계를 같이 고쳐야 한다.** 캐시를 켜면 캐시로 처리된 몫이 `input_tokens` 에서
  빠진다. `_estimate_cost` 에 캐시 항(쓰기 1.25배 · 읽기 0.1배)을 더하지 않으면 비용이
  실제보다 작게 나온다 — **아낀 것이 아니라 안 보이는 것이다.**

### 곁가지로 나온 개인정보 건 (J5)

화이트리스트를 걷어내자 `logger.info("tool_call", extra={"input": tu.input})` 이 실제로
찍히게 됐다. `search_applications` 의 `q` 에는 **지원자 이름·이메일이 들어온다.**
[J5](../02_tasks/J5-로깅-에러표준화.md)의 "로그에 이메일·전화를 남기지 않는다"에 걸린다
→ 값 대신 **인자 키 이름만** 남기도록 바꿨다(`tool_args`).

`extra` 키 이름도 주의한다. `args`·`module`·`name`·`message` 는 `LogRecord` 예약어라
`logging` 이 `KeyError` 를 던진다 — 로거 레벨이 INFO 로 올라간 경로에서만 터져서
단위 테스트를 따로 돌리면 안 잡힌다(실제로 이번에 전체 실행에서만 드러났다).

# ADR-0022. 프롬프트 체이닝 — 요약→평가→추천 단계별 파이프라인

> **상태: 확정 · 2026-08-31** · W3 착수 예정
> 관련: [ADR-0012 서류심사 AI 분류기준](0012-서류심사-AI-분류기준.md) · [ADR-0011 에이전트 모델 비용](0011-에이전트-모델-비용.md) · [ADR-0021 RAG 시맨틱 검색](0021-RAG-시맨틱-검색.md)

## 문제

현재 요약(`summarizer.py`)은 단일 프롬프트로 gist + fit + concerns를 한 번에 뽑는다. 단일 호출이라 단순하지만:

1. 프롬프트가 복잡해질수록 출력 품질이 떨어진다 (한 번에 여러 작업 요구)
2. 중간 결과를 재사용할 수 없다 (요약만 필요할 때도 전체를 다시 호출)
3. ADR-0012의 3그룹 분류(통과/검토/제외)를 넣으려면 단계별 판단이 필요하다

## 결정

요약을 3단계 체인으로 분리한다. 각 단계는 독립 프롬프트 + 독립 호출이다.

### 파이프라인

```
지원서 제출
  │
  ▼
[1단계: 요약] ─── 이력서+자소서 → 구조화 요약 (gist, skills_extracted, experience_summary)
  │
  ▼
[2단계: 평가] ─── 요약 + 채용공고 → 적합도 분석 (fit[], concerns[], score 1~5)
  │
  ▼
[3단계: 추천] ─── 평가 결과 → 3그룹 분류 (pass/review/reject) + 근거
```

### 각 단계 상세

| 단계 | 입력 | 출력 | 모델 | 비용/건 |
|------|------|------|------|---------|
| 요약 | name, education, career_years, skills, self_intro | `{gist, skills_extracted, experience_summary}` | Haiku | ~$0.001 |
| 평가 | 1단계 출력 + job posting title/description | `{fit[], concerns[], fit_score}` | Haiku | ~$0.002 |
| 추천 | 2단계 출력 | `{group: "pass"|"review"|"reject", reason}` | Haiku | ~$0.001 |

총 비용: ~$0.004/건 (현재 단일 호출 $0.001~0.005와 유사)

### 핵심 설계

- **단계별 독립 실행**: 요약만 필요하면 1단계만 호출, 전체 분류가 필요하면 3단계 모두 호출
- **중간 결과 저장**: 각 단계 출력을 `ai_summary` JSON에 구조화 저장 — 재호출 없이 재사용
- **실패 격리**: 2단계가 실패해도 1단계 결과는 유지
- **비용 가드**: 더미 데이터에서는 호출하지 않음 (ADR-0011), 실 지원서에서만 트리거

### 변경 대상

| 파일 | 변경 내용 |
|------|-----------|
| `backend/app/agent/summarizer.py` | 3단계 파이프라인으로 리팩토링 |
| `backend/app/agent/prompts/summarize.v1.md` | 단계별 3개 프롬프트로 분리 (summarize_step1.md, step2.md, step3.md) |
| `backend/app/models.py` | `ai_summary` JSON 구조 확장 (기존 호환 유지) |
| `backend/app/agent/tools/read.py` | `get_application` 반환에 `ai_group` 필드 추가 |

### ai_summary JSON 구조 (확장)

```json
{
  "v": 2,
  "step1": {"gist": "...", "skills_extracted": [...], "experience_summary": "..."},
  "step2": {"fit": [...], "concerns": [...], "fit_score": 4},
  "step3": {"group": "pass", "reason": "..."},
  "gist": "...",
  "fit": [...],
  "concerns": [...]
}
```

v1 호환: 기존 `gist`, `fit`, `concerns` 필드 유지. `v` 필드로 버전 구분.

## 범위에서 뺀 것

- 모델 분기 (단계별 다른 모델 사용) — 현재는 전부 Haiku, 품질 이슈 시 2단계만 상위 모델로 변경 가능
- 병렬 호출 — 단계 간 의존성이 있어 순차 실행. 여러 지원자를 동시에 처리하는 건 기존 백그라운드 태스크로 해결
- 피드백 학습 (ADR-0012 §2-2) — 데이터 축적 후 별도 판단

## 리스크

- API 호출 3회로 늘어나 지연 증가 — 백그라운드 태스크라 사용자 체감 없음
- 프롬프트 3개 관리 부담 — 단계별 역할이 명확해서 오히려 개별 개선이 쉬움
- ai_summary 구조 변경 — v 필드로 하위 호환 유지, 기존 데이터 마이그레이션 불필요

# ADR-0039. 서류 자동 탈락은 50점 미만만 — 임계 아래 B 구간은 보류

> **상태**: 확정 · 2026-10-19 · 작성 suvisdev (인프라·총괄). 백엔드(`app/application/screening.py`, 오너 woojeongalex)·에이전트(`app/agent/summarizer.py`, 오너 cloverky) 도메인 수정 — 사후 공지.
> **개정 대상**: [ADR-0034 에이전트 자동 심사](0034-에이전트-자동심사.md) 결정 1 "임계 미만이면 `applied → rejected`" — 자동 탈락을 **50점 미만**으로 좁힌다. 임계 이상 자동 통과, 수동 모드, 사람이 이기는 규칙, 불합격 메일 일괄은 그대로다.
> 관련: [B 등급 보정 실측](../07_eval/doc-score-b-band-2026-10.md)(PR #366) · [결정성 실측](../07_eval/doc-score-determinism-2026-10.md)(PR #365).

## 문제

PR #366 이 채점 프롬프트(`chain_evaluate.v4`)에 요건 점수 구간표를 넣어, fit-check 24명 중 기대 B(요건 일부 충족) 11명이 서류 50~69점 구간으로 올라왔다. 그런데 그중 7명이 **52~58점**이라 기본 임계 60 아래에서 전부 자동 탈락한다.

임계 60 은 B 구간(50~69) 한가운데 있다. B 는 요약 체인의 적합도 3이고, 3단계 추천(`chain_recommend`)은 이것을 **"추가 확인"** 으로 낸다. 아르가 스스로 "판단하려면 정보가 더 필요하다" 고 본 지원자를 아르 혼자 떨어뜨리고 있었다. 채용은 고위험 영역이라 경계선의 판단은 사람이 보는 편이 맞다.

## 선택지

|---|---|---|---|---|---|

## 결정

1. **자동 판정은 세 칸이다.** `doc_score ≥ 임계` → 통과(지금과 같음). `50 ≤ doc_score < 임계` → **보류**: 단계를 옮기지 않고 `doc_decision='hold'`, `doc_decided_at` 을 남긴다. `doc_score < 50` → 탈락(지금과 같음). 하한은 `screening.REVIEW_FLOOR = 50`.
2. **하한은 임계에서 몇 점 아래가 아니라 50 으로 고정한다.** 50 은 B 구간의 아래 끝이다 — "자동 탈락은 아르가 C(요건 충족 낮음)로 본 사람만" 이라는 한 문장으로 설명된다. 임계 80 처럼 높게 잡은 공고는 50~79 가 보류라 사람이 볼 몫이 늘지만, 그 공고가 높은 기준으로 거르려는 것은 **자동 통과**이지 50~79점 지원자를 자동으로 떨어뜨리는 것이 아니다. 임계가 50 이하인 공고에는 보류 구간이 없다.
3. **보류는 판정 시각을 남기고, 시각이 있는 보류는 아르가 다시 옮기지 않는다.** 요약 재생성 버튼(`decide_if_never_decided`)은 이미 그렇게 걸렀고, 이력서가 뒤늦게 붙어 요약이 다시 도는 경로(외부 연동 `resume_fetch.after_resume` → `decide_document`)도 같이 거른다 — 점수가 바뀌어도 사람이 옮긴다. 수동 모드 보류와 같은 취급이라, 수동 모드로 보류됐다가 공고가 자동으로 바뀐 지원자도 이 경로로 다시 옮겨지지 않는다(전에는 옮겨질 수 있었다). `doc_score_detail.review_floor` 에 하한을 같이 적는다(요약을 다시 만들면 내역이 새로 써져 사라진다).
4. **적합도 1~5점의 반올림을 .5 올림으로 고친다.** 지금은 `round()` 가 .5 를 짝수로 보내 서류 50 이 적합도 2(C), 90 이 4 였다. B 의 아래 끝이 51 로 밀려 결정 2 의 하한과 어긋났다. 이제 1: 0~29 · 2: 30~49 · 3: 50~69 · 4: 70~89 · 5: 90~100 (`summarizer.fit_score_from_doc`). 바뀌는 값은 서류 50·90 두 점뿐이다.

## fit-check 24명 — 판정 분포 (임계 60)

서류 점수는 PR #366 실측(`chain_evaluate.v4`, Haiku 4.5, temperature 0)을 그대로 쓰고 판정 규칙만 바꿔 셌다. 판정은 점수만으로 정해지므로 다시 호출하지 않았다.

| 기대 | 지금 규칙 (v3 점수) | 지금 규칙 (v4 점수) | **이 결정 (v4 점수)** |
|---|---|---|---|
| A 8명 | 통과 8 | 통과 8 | **통과 8** |
| B 11명 | 통과 1 · 탈락 10 | 통과 1 · 탈락 10 | **통과 1 · 보류 8 · 탈락 2** |
| C 5명 | 탈락 5 | 탈락 5 | **탈락 5** |

- 보류 8명: 박도윤 54 · 강현우 50 · 서지훈 52 · 문가영 52 · 임재원 53 · 남기훈 58 · 백서준 52 · 장우진 52.
- 여전히 탈락하는 B 2명: 신예은 42 · 오하람 38 (채점이 "다른 직무" 로 봄 — PR #366 문서의 남은 불일치).
- C 는 최고 37점이라 보류에 섞이지 않았다. A 는 최저 74점.
- 반올림 고침으로 강현우(50)의 적합도가 2 → 3 이 되어 기대 등급 일치는 21 → 22/24.
- v3 점수에 이 규칙만 얹으면 보류는 남기훈(59) 1명뿐이다. 이 결정은 PR #366 의 점수 보정과 같이 있어야 효과가 난다.

## 비용 · 리스크

- **담당자 일이 는다.** 보류자는 마감 뒤에도 `applied` 에 남는다 — 자동으로 정리되지 않는다. fit-check 기준 24명 중 8명. 목록 화면에 보류만 모아 보는 필터는 없다(프론트 후속 후보).
- **보류자에게는 아무 메일도 안 간다.** 사람이 옮기기 전까지 단계는 `applied` 그대로다.
- 이미 자동 탈락한 50~59점 지원자는 되살리지 않는다. 마감 전이고 메일이 안 나갔다면 담당자가 직접 옮길 수 있다(수동이 이긴다).
- 하한 50 은 상수다. 회사·공고별로 바꾸는 설정은 두지 않았다 — 필요해지면 `job_postings` 컬럼으로 뺀다.

## 되돌리기

`screening.REVIEW_FLOOR` 를 101 로 두면 보류 구간이 사라져 ADR-0034 그대로 돌아간다. 스키마·API 변경이 없으므로 코드만 되돌리면 된다. 반올림은 `fit_score_from_doc` 한 곳이다.

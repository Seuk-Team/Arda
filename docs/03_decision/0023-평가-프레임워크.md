# ADR-0023. 에이전트 평가 프레임워크 — 답변 품질 자동 측정

> **상태: 확정 · 2026-08-31** · 로컬 개발 시 진행 (일정 비종속)
> 관련: [ADR-0011 에이전트 모델 비용](0011-에이전트-모델-비용.md) · [ADR-0022 프롬프트 체이닝](0022-프롬프트-체이닝.md)

## 문제

에이전트 프롬프트를 수정할 때 품질이 나아졌는지 악화됐는지 판단할 기준이 없다. 수동으로 몇 개 질문을 던져보는 것이 전부다. 프롬프트 v2 개선(W3)과 RAG 도입 후 회귀를 잡으려면 자동화된 평가가 필요하다.

## 결정

로컬 개발 환경에서 실행하는 eval 스크립트를 만든다. CI에 넣지 않고 개발자가 프롬프트 변경 전후에 수동 실행한다.

### 구성

```
eval/
├── cases/              # 평가 케이스 (YAML)
│   ├── search.yaml     # 검색 시나리오
│   ├── stage.yaml      # 단계 변경 시나리오
│   ├── schedule.yaml   # 일정 도구 시나리오
│   └── edge.yaml       # 엣지 케이스 (권한 거부, 모호한 요청 등)
├── judge.py            # 판정 로직 (LLM-as-judge + 규칙 기반)
├── runner.py           # 케이스 실행 + 결과 수집
└── report.py           # 결과 비교 리포트 생성
```

### 평가 케이스 형식

```yaml
- id: search_by_name
  input: "김도현 찾아줘"
  expect:
    tool_called: search_applications
    tool_args:
      q: "김도현"
    response_contains: ["김도현"]
    response_not_contains: ["모르겠", "찾을 수 없"]

- id: reject_without_reason
  input: "홍길동 불합격 처리해줘"
  expect:
    tool_called: change_stage
    tool_args:
      to_stage: rejected
    response_contains: ["사유"]
    pending_action: true
```

### 판정 방식

| 판정 유형 | 방식 | 비용 |
|-----------|------|------|
| 도구 호출 정확도 | 규칙 기반 — 호출된 도구·인자 비교 | 무료 |
| 응답 포함/미포함 | 규칙 기반 — 키워드 포함 여부 | 무료 |
| 응답 품질 | LLM-as-judge — Haiku로 1~5점 | ~$0.002/건 |
| 할루시네이션 | 규칙 기반 — 도구 결과에 없는 정보 생성 여부 | 무료 |

### 실행 방식

```bash
# 전체 실행
python -m eval.runner --all

# 특정 카테고리만
python -m eval.runner --cases search

# 프롬프트 변경 전후 비교
python -m eval.runner --all --tag before
# (프롬프트 수정 후)
python -m eval.runner --all --tag after
python -m eval.report --compare before after
```

### 리포트 출력

```
=== Eval Report: before vs after ===
총 케이스: 30
도구 정확도: 93% → 97% (+4%)
응답 품질:  3.8 → 4.1 (+0.3)
할루시네이션: 2건 → 0건
회귀: 0건
```

### 변경 대상

| 파일 | 변경 내용 |
|------|-----------|
| `backend/eval/` | 신규 디렉토리 — 평가 프레임워크 전체 |
| `backend/eval/cases/*.yaml` | 평가 케이스 30~50개 |
| `backend/eval/runner.py` | 케이스 실행 + mock DB 환경 |
| `backend/eval/judge.py` | 규칙 판정 + LLM-as-judge |
| `backend/eval/report.py` | 결과 비교 리포트 |

## 범위에서 뺀 것

- CI 자동 실행 — LLM 호출 비용 + 실행 시간 때문에 로컬 수동 실행만
- A/B 테스트 — 운영 환경 필요, 현재 로컬 개발 단계에서는 불필요
- 사용자 피드백 수집 — 실 서비스 런칭 후 검토

## 리스크

- LLM-as-judge 자체의 판정 편향 — 규칙 기반 판정을 우선하고, LLM 판정은 보조로만 사용
- 평가 케이스 유지 보수 — 도구 추가/변경 시 케이스도 업데이트 필요
- mock DB 환경 구축 비용 — 기존 테스트 fixture 재사용

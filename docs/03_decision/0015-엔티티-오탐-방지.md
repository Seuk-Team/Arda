# ADR-0015. 엔티티 리졸버 한글 수사 오탐 방지

- 상태: **확정** (2026-08-27) — PR #130 으로 반영
- 작성: suvisdev (에이전트)
- 선행: [ADR-0004](0004-음성-stt만.md) · [role/agent.md](../01_role/agent.md) §STT

## 맥락

`entity_resolver.py`의 `normalize_numbers()`는 한글 수사를 아라비아 숫자로 변환한다.
예: "경력 이년 이상" → "경력 2년 이상"

문제는 한글 수사 글자(이, 사, 오, 일, 구)가 일상 단어에도 쓰인다는 점이다.
기존 로직은 이를 구분하지 못해 **오탐(false positive)**이 발생했다.

### 오탐 사례

| 입력 | 기존 출력 (오탐) | 원인 |
|------|------------------|------|
| "이번 면접" | "2번 면접" | "이" → 2 + 카운터 "번" |
| "사건 종료" | "4건 종료" | "사" → 4 + 카운터 "건" |
| "신입 사원" | "신입 4원" | "사" → 4 + 카운터 "원" |
| "이사회 결정" | 숫자 변환 시도 | "이"+"사" 모두 수사 글자 |

이 오탐은 STT(음성) 경로에서만 발생한다. 텍스트 채팅에서는 PR #129로 `resolve_entities`를 제거했기 때문에 해당 없다.

## 검증한 것

### 1. 오탐 단어 분석

한글 수사 1글자(`이`=2, `사`=4, `오`=5, `일`=1, `구`=9) × 카운터 조사(`년`, `건`, `원`, `번`, `회`, `일`, `명`, `대` 등) 조합을 전수 조사해서 일상 단어와 충돌하는 13개를 식별했다.

```
_SINO_FALSE_POSITIVES = frozenset({
    "이번", "이점", "이대",                          # 이(2)
    "사건", "사회", "사원", "사장", "사대", "사채",   # 사(4)
    "오일",                                          # 오(5)
    "일대", "일원",                                  # 일(1)
    "구원", "구명",                                  # 구(9)
})
```

**선정 기준:**
- ATS 도메인(채용·면접·인사)에서 자주 쓰이는 단어 우선
- "삼"(3), "육"(6), "칠"(7), "팔"(8)은 카운터 조합 시 일상 단어가 없어 제외
- "영"(0)은 카운터 앞에 오는 경우가 사실상 없어 제외

### 2. 방어 로직 설계

두 가지 레이어로 방어한다:

**레이어 1 — 구조 검사 (다중 글자)**
```python
if len(matched) >= 2 and not any(ch in _SINO_SCALES for ch in matched):
    return matched  # 단위 글자만으로 된 조합은 숫자가 아님
```
"이사", "구명" 처럼 2글자 이상인데 `십/백/천/만/억`이 없으면 실제 숫자가 아니라 단어다.
예: "이사" = "이"(2) + "사"(4) 이지만 "24"가 아닌 일상 단어.
단, "이십"은 "십"이 있으므로 정상 변환(→ 20).

**레이어 2 — 사전 검사 (단일 글자)**
```python
if len(matched) == 1:
    after = text[m.end():].lstrip()
    if after and matched + after[0] in _SINO_FALSE_POSITIVES:
        return matched  # "이" + "번" = "이번" → 변환 안 함
```
정규식이 수사 1글자만 매칭하고 뒤에 카운터가 올 때, 수사+카운터 조합이 오탐 사전에 있으면 변환하지 않는다.

**설계 근거:**
- 레이어 1만으로는 단일 글자 + 카운터 케이스를 못 막음 ("이" + "번")
- 레이어 2만으로는 다중 글자 조합을 못 막음 ("이사회")
- 두 레이어가 서로 다른 패턴을 커버하므로 둘 다 필요

### 3. 실제 숫자 변환 보존 확인

오탐 방지가 정상 변환을 깨뜨리지 않는지 검증:

| 입력 | 출력 | 판정 |
|------|------|------|
| "경력 이년 이상" | "경력 2년 이상" | ✅ "이" + "년"은 사전에 없음 |
| "삼백이십오 명" | "325 명" | ✅ "십"이 있으므로 레이어 1 통과 |
| "이번 면접에서 삼년 경력자" | "이번" 유지 + "3년" 변환 | ✅ 혼합 케이스 정상 |

### 4. 테스트 커버리지

기존 8개 + 추가 10개 = **18개 테스트** (`TestNormalizeNumbers` 클래스)

추가된 테스트:
- 오탐 단어 7개 개별 테스트 (이번, 사건, 이점, 사회, 사원, 이대, 사장)
- 다중 글자 단위 조합 ("이사회")
- 실제 숫자 변환 보존 ("이년" → "2년")
- 혼합 케이스 ("이번" 유지 + "삼년" → "3년")

전체 테스트 스위트 118개 통과 확인.

## 한계·후속

- 사전에 없는 새로운 오탐 단어가 나올 수 있다 → 운영 로그에서 모니터링 후 사전에 추가
- 현재 방어는 "수사 + 바로 뒤 1글자" 조합만 검사한다. "이번에"처럼 조사가 붙으면 "이" + "번" 매칭이 아예 안 되므로 문제없지만, 새로운 패턴이 나오면 로직 확장 필요
- 오탐 수정 완료 후 텍스트 채팅 경로에도 `resolve_entities` 재연결 (PR #130)

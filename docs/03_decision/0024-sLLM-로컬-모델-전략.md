# ADR-0024. sLLM 로컬 모델 전략 — 하이브리드 구성

> **상태: 검토 중 · 2026-08-31** · 모델 선정은 W3 착수 시 GPU 사양 확인 후 확정
>
> **2026-09-01 실측이 아래 [개정 절](#2026-09-01-개정--실측으로-드러난-것)에 붙었다.** 원문의 GPU 전제(RTX 3060 12GB 이상)가 실제 장비(RTX 3050 8GB)와 달라 결론이 바뀐다.
> 관련: [ADR-0011 에이전트 모델 비용](0011-에이전트-모델-비용.md) · [ADR-0021 RAG 시맨틱 검색](0021-RAG-시맨틱-검색.md) · [ADR-0022 프롬프트 체이닝](0022-프롬프트-체이닝.md)

## 문제

현재 에이전트의 AI 호출은 전부 외부 API(Claude, OpenAI Whisper)를 거친다. 채용 데이터는 지원자 개인정보(이름, 연락처, 학력, 경력, 자기소개서)를 포함하며 기업의 가장 민감한 자산 중 하나다. 소주제 2번에서 "데이터 반출 없는 채용 에이전트"를 요구하고 있고, 소주제 4번에서 "STT → RAG → sLLM" 파이프라인을 명시했다.

## 결정

민감 작업은 로컬 sLLM으로, 일반 작업은 API로 나누는 **하이브리드 구성**을 채택한다. 모델은 전부 오픈소스/무료이며, Ollama로 로컬 구동한다. 최종 모델 선정은 서버 GPU 사양 확인 후 확정한다.

## 용도별 모델 후보

### 1. 대화 + 도구 호출 (에이전트 코어)

현재 Claude API가 담당. sLLM 전환 시 후보:

| 모델 | 크기 | VRAM | 한국어 | tool_use | 비고 |
|------|------|------|--------|----------|------|
| Llama 3.1 8B | 8B | ~6GB | 양호 | 지원 | 범용 성능 최상, 커뮤니티 최대 |
| EXAONE 3.5 7.8B | 7.8B | ~6GB | 최상 | 제한적 | LG, 한국어 특화 |
| Gemma 2 9B | 9B | ~7GB | 양호 | 미지원 | Google, 추론 능력 우수 |

**하이브리드 옵션**: GPU 부족 시 Claude API 유지 + 민감 데이터만 마스킹 처리

### 2. 면접 요약 + 분석 (STT 후처리)

소주제 4번 "RAG → sLLM" 파이프라인의 sLLM 부분:

| 모델 | 크기 | VRAM | 특징 |
|------|------|------|------|
| Qwen 2.5 7B | 7B | ~5GB | 128K 컨텍스트, 면접 전사본 전체 입력 가능 |
| Phi-4 Mini 3.8B | 3.8B | ~3GB | 초경량, CPU에서도 동작, 한국어 보통 |

### 3. 임베딩 (RAG 검색용)

| 모델 | 차원 | 한국어 | 실행 환경 |
|------|------|--------|-----------|
| ko-sroberta-multitask | 768 | 전용 | CPU OK (~50ms/건) |
| BGE-M3 | 1024 | 100+언어 | CPU OK (~80ms/건) |

### 4. STT (음성 전사)

| 모델 | VRAM | 특징 |
|------|------|------|
| Whisper large-v3 (로컬) | ~4GB | 현재 API → 로컬 전환. 오픈소스, 무료 |
| faster-whisper | ~2GB | CTranslate2 최적화, 4배 빠름, 동일 품질 |

## 실행 환경별 구성

모델을 동시에 전부 올리지 않는다. Ollama가 미사용 모델을 자동 언로드하며, 실사용 시 6~8GB면 충분하다.

### GPU 있는 경우 (RTX 3060 12GB 이상)

```
[채팅] Llama 8B 로컬 → 도구 호출 → DB
[접수] ko-sroberta 임베딩 (CPU) → pgvector
[면접] faster-whisper 로컬 → RAG 검색 → Qwen 7B 요약
```

전구간 로컬 — 외부 API 호출 0, 운영 비용 0원

### GPU 없거나 약한 경우

```
[채팅] Claude API 유지 (하이브리드) → 도구 호출 → DB
[접수] ko-sroberta 임베딩 (CPU) → pgvector
[면접] faster-whisper CPU → RAG 검색 → Claude API 요약
```

임베딩과 STT는 CPU로 동작, 추론만 API 사용

## 2026-09-01 개정 — 실측으로 드러난 것

> 원문은 고치지 않았다. 원문은 **장비를 보기 전에** 쓴 것이고, 그 전제가 틀렸다는 것이 이 절의 내용이다.
> 근거: 브랜치 `worktree-agent-a867fab28aeed20e1` (어댑터 프로토타입) · RTX 3050 8GB · 실제 DB 지원자 500건 · 실제 도구 실행.

### 1. GPU 전제가 틀렸다

원문은 "RTX 3060 12GB 이상"을 GPU 있는 경우로 잡았다. **실제 장비는 RTX 3050 8GB**다. 메모리 대역폭이 3060 Ti의 절반 수준이라 원문의 "GPU 있는 경우 = 전구간 로컬" 구성은 그대로 성립하지 않는다.

### 2. 속도 실측 — 같은 질의, 같은 DB, 같은 도구

| 질의 | `claude-haiku-4-5` | `qwen3:4b` | `qwen3:8b` |
|---|---|---|---|
| 읽기 도구 1개 ("면접 단계 지원자 보여줘") | **13.6초** | 73.2초 | 107.5초 |
| 쓰기(확인 카드까지) | **2.9초** | 32.6초 | 31.0초 |
| 도구 연쇄 시도 | **6.6초** | 86.8초 | 130.5초 |
| 출력 tok/s | 106 | 45 | 7.4 |

- **8B는 탈락.** VRAM 8GB에 올라가긴 하지만 tok/s가 4B의 1/6이다. 원문 후보표의 8B급(Llama 3.1 8B · EXAONE 7.8B · Gemma 2 9B)은 이 장비에서 같은 벽에 부딪힌다.
- **4B도 지금 구조로는 대화형에 못 쓴다.** 담당자가 33~87초를 기다린다.

### 3. 병목은 프롬프트가 아니라 출력 길이였다

전환 논의는 "고정 프리픽스 17KB가 무겁다"에서 출발했는데, 실측은 다른 곳을 가리킨다. 같은 질의에서 **`qwen3:4b`가 3,248 출력 토큰을 쓰는 동안 haiku는 1,450 토큰**을 썼다. 지원자 10명을 이메일·경력·기술까지 전부 나열하기 때문이다. 45 tok/s에서 3천 토큰은 그 자체로 70초다.

사고 모드(`<think>`)를 의심해 껐지만 출력은 3,444 → 3,248로 거의 그대로였다 — **원인이 아니다.** 토글은 `OLLAMA_THINK`로 남겨 뒀다.

즉 프롬프트를 줄이는 것보다 **응답을 짧게 만드는 것**(도구 결과 필드 축소 · 나열 상한 · 출력 형식 고정)이 먼저다.

### 4. 어댑터 동작은 정상

`AGENT_CHAT_BACKEND` / `AGENT_SUMMARY_BACKEND` 역할별 스위치, `<think>` 제거, 도구 스키마 변환, 단일 GPU 직렬화 락, `num_ctx` 명시. 스모크에서 `<think>` 누출 0 · 도구 선택 정확 · **쓰기는 확인 카드로만**(실행 안 함) · `ollama:` 태그 · `cost_usd` 0.0. 테스트 362 passed(main 312 + 신규 50).

### 5. 도구 연쇄는 예상대로 안 된다

"Python 경험자 중 면접 안 잡힌 사람"은 `search_applications` 한 번에서 끝난다. 중간 결과로 다음 도구를 정하는 계획이 4B로는 서지 않는다. 이 유형을 데모에 넣을지가 **로컬 단독이냐 하이브리드냐**를 가른다.

### 6. 그래서 남은 선택지

원문의 "GPU 있는 경우 = 전구간 로컬"은 이 장비에서 성립하지 않는다. 실질 선택지는 셋이다.

| 안 | 내용 | 대가 |
|---|---|---|
| A | **응답 길이부터 줄이고 4B 재측정** | 가장 싸다. 3천 → 500 토큰이면 4B가 10초대로 들어온다 |
| B | **하이브리드 유지** — 요약·임베딩·STT만 로컬, 채팅은 API | "데이터 반출 없음"이 채팅에서 깨진다 |
| C | **GPU 있는 장비 확보** | 원문 전제로 복귀. 운영 EC2(t3.micro)는 어차피 대상이 아니다 |

**A를 먼저 한다.** B·C는 A의 재측정 뒤에 판단할 것.

### 7. 이 절이 못 채운 것

- 요약 체인(3단, 프롬프트 1.5KB×3)의 로컬 품질·속도 — 미측정
- 임베딩 BGE-M3 교체 — 미착수 (`ko-sroberta`의 `max_seq_length=128` 제약은 그대로)
- 도구 선택 **정답률** — 이번엔 속도만 쟀다. ADR-0023 eval 프레임워크가 필요하다
- `확정일`·`확정자`는 여전히 빈칸이다. 소개문 2번의 정식 범위 여부가 선행이다

### 8. A안 실행 결과 — 60초가 11~17초가 됐다

같은 조건(RTX 3050 8GB · DB 지원자 500건 · 실제 도구 실행 · 웜업 후).

| 질의 | `claude-haiku-4-5` | `qwen3:4b` 최적화 전 | **`qwen3:4b` 최적화 후** |
|---|---|---|---|
| 읽기 도구 1개 | 13.6초 | 60.4초 | **16.9초** |
| 쓰기(확인 카드) | 2.9초 | 42.9초 | **3.5초** |
| 도구 연쇄 시도 | 6.6초 | 69.0초 | **11.2초** |
| 출력 토큰(읽기) | 1,450 | 2,653 | **252** |

**핵심 인과는 문법 제약이다.** 진단이 먼저였다 — `qwen2.5:3b`의 무응답은 `/api/chat` 원문이 `content: ""`, `eval_count: 1`, 즉 **첫 토큰으로 EOS**였다. 변인 분리 결과 잘림도 파싱 문제도 아니고 **긴 한국어 시스템 프롬프트(6.4K자) + tools 조합에서 형식이 붕괴**하는 것이었다(도구를 빼면 정상, 프롬프트를 줄여도 정상, `temperature 0`이면 결정적으로 붕괴).

Ollama `format`에 결정 스키마(`{action: tool|reply, ...}`)를 걸어 형식을 강제하니 붕괴가 사라졌고, **4B에서는 연쇄 효과가 났다** — 문법이 `<think>` 누출을 원천 차단하므로 **사고 모드를 꺼도 안전해졌다.** 60초의 정체가 사고 토큰이었으니 그게 통째로 없어졌다. 지우는 것과 안 만드는 것의 차이다.

곁들여 도구 결과도 줄였다: `search_applications` 10건 기준 키워드 2,072 → 1,288자(−38%), 시맨틱 2,665 → 1,252자(−53%). `email`·`created_at`·`similarity`를 뺐고 `id`(후속 도구 인자)와 `note`(폴백 안내 — 빼면 아르가 "지원자 없음"이라 단정한다)는 남겼다. 압축은 도구 계층에 있고 기본이 꺼짐이라 **Anthropic 경로 응답은 바이트 단위로 동일하다.**

### 9. 그래도 남은 한계 셋

1. **`qwen2.5:3b`는 못 쓴다.** 문법 제약이 무응답은 완치시켰지만 "10명"을 "5명"이라 하고 도구가 주지 않은 학력을 지어낸다. **형식이 아니라 능력 문제라 문법으로 안 잡힌다.** 3B 급은 여기서 접는다.
2. **도구 연쇄는 여전히 안 된다.** "Python 경험자 중 면접 안 잡힌 사람"을 `search_applications` 한 번으로 끝내고 "면접 단계 지원자 10명"으로 재구성한다. 지어내지 않는 건 좋지만 질문에 답한 것은 아니다.
3. **스트리밍과 문법 제약은 같이 못 쓴다.** 구조화 모드는 출력이 JSON이라 파싱 전에는 흘릴 문장이 없다. 스트리밍은 "느린 경우"를 위해 만들었는데 그 느린 경우가 없어졌다 — 구조화를 쓰지 않는 구성과 요약 체인에만 남는다.

### 10. 어디에 API 를 쓰고 어디에 로컬을 쓸까 — 스위치는 이미 역할별이다

| 역할 | 스위치 | 기본 | 권고 |
|---|---|---|---|
| 채팅(도구 호출) | `AGENT_CHAT_BACKEND` | `anthropic` | 데모는 `ollama`, 운영은 `anthropic` |
| 요약(접수 1회) | `AGENT_SUMMARY_BACKEND` | `anthropic` | **로컬 1순위** — 비동기라 지연이 안 보이고 개인정보가 가장 많다 |
| 임베딩 | `EMBEDDING_MODEL` | `ko-sroberta` | **이미 로컬** |
| STT | `WHISPER_MODEL` | `whisper-1`(API) | `faster-whisper` 로 전환 |

모르는 백엔드 이름은 조용히 폴백하지 않고 `ValueError` 로 터진다 — 오타 하나로 로컬인 줄 알고 클라우드에 과금되는 것을 막는다.

**질의 난이도에 따른 자동 폴백은 넣지 말 것.** "연쇄 질의는 자동으로 Claude 로" 는 편해 보이지만, 담당자가 **자기 질문이 언제 외부로 나갔는지 알 수 없게 된다.** 소개문 2번이 약속한 "데이터 반출 없음"은 그렇게 깨진다. 대신 명시적으로 한다 — 로컬이 못 풀면 "이 질문은 로컬 모델로 답하기 어렵습니다. 클라우드로 다시 시도할까요?" 를 띄우고 **사람이 누른다.** [ADR-0003](0003-ai-추천만.md) 확인 카드와 같은 원리다. 응답에 어느 백엔드가 답했는지는 `ChatResponse.backend` 로 이미 나가므로 화면에 배지로 붙이면 된다.

### 11. 실적용 범위 — 운영 서버에는 못 올린다

**로컬 스택은 실적용 가능하다.** 테스트 387 통과, 기본값(env 미설정)이면 Anthropic 경로가 지금과 동일하게 동작하고, 스위치 하나로 갈린다.

**단 운영 EC2(t3.micro · RAM 1GiB · GPU 없음)에는 못 올린다.** 로컬 모델은 GPU 있는 장비 전제다. 즉 지금 구성으로 말할 수 있는 것은:

- **발표·데모에서 로컬로 돌리는 것** — 가능. GPU 있는 PC 에서 `AGENT_CHAT_BACKEND=ollama` 하나로 전환된다 *(2026-09-02: 이 문서가 전제한 팀장 PC(RTX 3060 Ti)는 팀에서 빠졌다 — 팀 안의 GPU PC 를 다시 정해야 한다)*
- **arda.seuk.cloud 운영에 적용** — 불가. GPU 인스턴스를 따로 두지 않는 한

**발표에서 이 둘을 구분해 말하지 않으면 질문받는다.**

### 12. 이 절이 여전히 못 채운 것

- 요약 체인의 로컬 품질 — 속도는 비동기라 무관하지만 **품질을 안 쟀다.** 다음 순서는 여기다
- 도구 선택 **정답률** — 이번에도 속도와 접지(사실 일치)만 봤다. [ADR-0023](0023-평가-프레임워크.md) eval 이 필요하다
- 임베딩 BGE-M3 교체 — 미착수
- `확정일`·`확정자` — 소개문 2번의 정식 범위 여부가 선행이다

### 13. 배포 형태 — 통일하지 않고 둘을 지원한다 (2026-09-01 오후 결정)

"온프레미스로 완전히 통일하면 더 의미 있지 않나"에서 출발해, **통일이 아니라 배포 형태를 둘로 두는 것**으로 정리했다.

**통일이 순증이 아니기 때문이다.** EC2 를 버리면 배포 파이프라인·권한 모델 스토리를 **잃고** 온프레미스 스토리를 **얻는** 교환이 된다. 발표에서 말할 것이 늘지 않고, 잃는 쪽이 팀장 도메인이며([04-team](../00_overview/04-team.md) 발표 역할표), W3 예정인 CI/CD(J4)가 통째로 무의미해진다. 반면 두 형태를 지원하면 **J4 가 "두 타깃 빌드"가 되어 오히려 커진다.**

그리고 코드는 이미 그렇게 돼 있다 — 역할별 백엔드 스위치(§10)가 전역이 아니라 역할별이라 중간 상태를 만들 수 있다. 남은 것은 배포 껍데기뿐이다.

| 형태 | 무엇 | 쓰는 곳 |
|---|---|---|
| SaaS 판 | 지금 구성 (EC2 + Vercel + S3/SES/SQS) | 09/04 게이트·상시 운영 |
| 온프레미스 판 | `docker-compose.onprem.yml` — 한 대에 전부 | 발표 시연·"데이터 반출 없음" 근거 |

#### 추론 장비 — 상시 PC 로 간다

**AWS 크레딧($400)을 아끼기 위해 상시 켜 두는 PC 한 대를 팀 공용 추론 서버로 쓴다.** GPU 인스턴스(`g4dn.xlarge`)는 필요할 때만 켠다.

- 이게 **오늘 성립하게 된 것**이다. 60 초짜리를 여럿이 공유하면 대기가 곱해져 못 썼는데, 11~17 초가 되면서 공유가 성립한다(§8)
- 팀원은 Ollama 를 각자 깔 필요가 없다. `OLLAMA_HOST` 로 그 장비를 가리키되 **포트를 열지 말고 SSH 터널**을 쓴다 — Ollama 에는 인증이 없고 그 포트로 지원자 정보가 오간다
- 상시 서버라면 `OLLAMA_KEEP_ALIVE=-1`(유휴 언로드 방지, 안 하면 첫 요청 +13초)과 `OLLAMA_NUM_PARALLEL=1`(어댑터의 직렬화 락은 프로세스 내부라 원격에선 무의미하다)을 걸어야 한다
- **운영 경로에는 넣지 않는다.** EC2 가 그 PC 를 부르면 인터넷을 건너 데이터 반출 문제가 원점으로 돌아간다. 운영에서도 로컬 추론이 필요해지면 그때 `g4dn.xlarge` 를 같은 VPC 에 둔다 — 크레딧으로 커버되고, 토큰당 비용이 0 이며, 끈 동안에도 EBS 비용만 남는다

#### 온프레미스 판에 아직 없는 것 셋

되는 것: DB · 파일(MinIO) · 채팅·요약 추론 · STT · 임베딩. 안 되는 것:

| | 대체 | 난이도 | 스펙 부담 |
|---|---|---|---|
| 프론트 서빙 (Vercel) | FastAPI `StaticFiles` 또는 nginx | 쉬움 (~1시간) | 없음 |
| 메일 발송 (SES) | `smtplib` + 고객사 SMTP | 중간 (반나절) | 없음 |
| 메일 큐 (SQS) | `EmailLog` 테이블 폴링 | 쉬움 (반나절) | 없음 |

**스펙은 문제가 아니다.** 16GB RAM·8GB VRAM 이면 전부 올라간다. 합쳐서 하루 남짓의 작업량이다.

두 가지는 순이득이라 짚어 둔다. **프론트를 API 가 서빙하면 같은 출처가 되어 CORS 자체가 필요 없어진다.** 그리고 **SES 도 SMTP 엔드포인트를 제공하므로 `smtplib` 로 갈아타면 SaaS 판과 온프레미스 판이 같은 코드를 쓴다** — 지금의 boto3 분기가 사라진다.

#### 메일은 범위를 좁혀 말한다

자체 메일 서버를 세우는 것은 하지 않는다. SPF·DKIM·IP 평판 때문에 도착률이 처참한, 하드웨어가 아니라 인터넷 생태계의 문제다. 실제 온프레미스 제품이 하는 것은 **SMTP 설정을 열어 주는 것**이고 고객사는 이미 자기 메일 서버가 있다.

발표에서의 주장도 그에 맞춘다 — **"지원자 데이터와 AI 추론은 이 장비를 벗어나지 않습니다. 메일 발송만 외부 SMTP 를 씁니다."** 메일은 어차피 지원자에게 나가는 것이 목적이라 반박당하지 않는다. 넓게 말하고 구멍을 잡히는 것보다 낫다.

#### 시기

**09/04 게이트 전에는 착수하지 않는다.** 게이트 4항목이 배포 URL 기준이라 지금 갈아엎으면 못 닫는다. W3 과제이고 순서는 어댑터 머지(완료) → 프론트 서빙 → SMTP → 큐. 작업 큐는 [role/infra](../01_role/infra.md).
